## 行為規格

| 項目 | 說明 | 範圍／限制 |
|---|---|---|
| 監看範圍 | 預設監看自己的與組織的 repo；fork 與協作 repo 預設略過，設定可以開啟 | 自動略過：已靜音、已封存、已停用、fork、協作、超過 90 天沒有活動（且本地沒有 90 天內的 run）、沒有 workflow、workflow 全部停用。封存、停用、沒有 workflow、workflow 全部停用這四種不能強制納入 |
| 輪詢（自動模式） | 每個 repo 各自排程，輪詢請求帶 `If-None-Match`（ETag）；另外每 30 秒探測一次哪些 repo 剛 push | 有 run 在跑：15 秒；安靜時：距最後活動的秒數 ÷ 30，夾在 30–300 秒；螢幕鎖定時至少 300 秒。選了固定秒數時改用該秒數，見[使用說明](usage.zh-TW.md)的「調整自動更新」 |
| 新 run 出現的時間（自動模式） | push 觸發的 run，建立後約 30 秒內出現 | push 後 15 分鐘內該 repo 每 30 秒輪詢；排程、手動觸發、重跑不會改變 push 時間，靠 repo 自己的輪詢，安靜的 repo 最多延遲 5 分鐘 |
| 鎖定、睡眠、喚醒 | 鎖定時所有間隔至少 300 秒，通知暫存；睡眠期間不送請求 | 解鎖、喚醒、離線恢復後立即全量刷新。喚醒除了 Windows 的喚醒事件，相鄰兩次每秒 tick 的間隔超過 120 秒也當成剛喚醒（推論，未實測：無人值守喚醒可能沒有喚醒事件）。全量刷新是 push 探測、所有監看中 repo 的 runs 與 PR 清單排成立即到期，照樣帶 ETag、受每分鐘上限控制；等權限錯誤或 404 重試的目標不提前；repo 完整清單與 workflow 清單照原本週期，例外是還沒查過 workflow 清單的監看中 repo：改成立即補查一次 workflow 清單，有 workflow 才接著抓 runs 與 PR 清單。暫停中這次執行還沒抓完過 repo 清單時（例如資料庫剛重建、以暫停模式啟動），全量刷新用一輪完整清單代替 push 探測；清單在等 403／404 重試或重建資料庫的退避期間照舊送探測 |
| API 額度 | 和 gh、其他工具共用每小時 5,000 次 | 回 304 不扣主額度；輪詢一次只送一個請求（另一條給複製 log 與寫入），每分鐘最多 60 個；剩餘低於 25% 時所有間隔拉長 2–8 倍 |
| 寫入（重跑、取消） | 只在開啟寫入功能、在確認對話框按下執行之後才送 `POST`；不送 body、不帶 ETag、不讀寫快取 | 兩個寫入之間至少隔 1 秒，也算進每分鐘 60 個；排隊超過 15 秒就放棄（沒有送出）；未登入、API 版本錯誤、限流暫停、離線時不送（自動更新「暫停」時照送）；轉址一律不跟隨；不自動重送，唯一的例外是 401 後換到新的 token 時重送一次；GitHub 回 5xx 時可能已經生效，算結果不確定，不算被拒。送出後（含被拒與結果不確定）立刻查一次這筆 run；重跑追蹤到看見新的嘗試或 run 變成未完成（超過 5 分鐘而且查過 3 次仍看不到就放棄；只看到未完成時見[已知限制第 29 項](known-limitations.zh-TW.md)），已受理的取消追蹤到 run 完成 |
| 追蹤的 run（決定系統匣顏色） | 每個 workflow 在預設分支的最新 run，加上每個開啟中 PR 分支 × 每個 workflow 的最新 run | 較舊的失敗只有被較新的成功取代才不算；取消、略過不會取代失敗；PR 關閉後不再追蹤；超過 90 天的失敗不算；停用的 workflow 不追蹤 |
| 整體狀態 | 失敗 > 進行中或排隊（含等待核准）> 全部成功 > 無資料 | 只有取消或略過結論的追蹤項目不會讓狀態變綠，也不會阻擋綠燈；連線問題用角標疊加，不改顏色 |
| 通知 | 追蹤中的 run 失敗；你觸發（`actor` 是你）的 run 成功；你標記「完成時通知我」的 run 完成；在 App 內重跑的 run，新的一次完成（自動當成「完成時通知我」） | 三項可分別關閉（重跑後的通知照「完成時通知我」那一項）；同一個 run 的同一次嘗試與結論只通知一次，重啟後也不重發；程式啟動前就完成的 run 不通知（「完成時通知我」例外）；2 秒內的通知合併成一則 |
| 提示視窗 | 自製視窗，主螢幕工作區右下角（離邊 16 DIP）、置頂、不搶焦點、不出現在工作列 | 失敗停留 12 秒（3–120）、成功與灰色結論 5 秒（2–60）；滑鼠停留時暫停計時。彙總提示的標題是「N 筆執行有變化（X 失敗、Y 成功、Z 其他）」（數量是 0 的不列），最多列 5 行，其餘顯示「還有 N 筆」；點擊行為見[使用說明](usage.zh-TW.md)。鎖定期間暫存，解鎖後合併成一則「鎖定期間的變化」。不用 Windows 系統通知（會被專注輔助吃掉） |
| 檢查新版本 | 距離上次完成的檢查滿 3 天，或從沒檢查過時，用你的 token 向 GitHub 查本專案最新的 release（`GET /repos/marvin3991/is-it-green-yet/releases/latest`）；比目前版本新（去掉 tag 的 `v` 與目前版本的 build metadata，照 SemVer 比較）就跳出提示，點了開該 release 的頁面。只通知，程式不會自己下載或替換。預設開啟；在設定頁關閉「定期檢查新版本（每 3 天）」後，完全不送這個請求 | 是否到期看 UTC 牆上時間，每小時在本機判斷一次（不連網），登入驗證成功（含啟動時）、喚醒、解鎖之後也各一次；上次檢查時間在未來時視為到期。200、304、404 算完成。失敗之後，或到期時正好離線、限流暫停、API 版本錯誤，最快 1 小時後才重試（剛喚醒時網路常常還沒起來，可能碰上這種情況）。未登入與睡眠期間跳過。自動更新「暫停」時照常檢查。完成過一次檢查之後才帶 ETag；走輪詢那條線，也算進每分鐘 60 個，但回應不更新額度與「最後更新」。同一個版本只通知一次，重啟後也不重發；不受三項通知開關影響，停留時間同失敗的提示（預設 12 秒）。`/releases/latest` 不會回 prerelease 與 draft，所以這兩種不會通知。請求進行中才關閉選項時，結果整個丟棄；重新開啟後最晚 1 小時內接手 |
| 耗時 | `updated_at − run_started_at` | 官方沒有定義這兩個欄位的語意，屬推論 |
| 預估剩餘時間 | 同 repo、同 workflow 最近 10 筆成功 run 耗時的中位數 | 只收第一次執行的成功（重跑的成功不算，只重跑失敗的 job 時耗時通常比較短）；少於 3 筆不預估；顯示「約剩 N m」（以分鐘無條件進位），超過時顯示「超過預估約 N m」 |
| 開始時間 | 一律用本地時區 | 剛剛（60 秒內或時鐘誤差）／N 分鐘前／今天 HH:mm／M/d HH:mm／yyyy/M/d |
| 清單內容 | 每個監看中 repo 最近 30 筆 run，加上追蹤中的 run、標記「完成時通知我」的 run，以及不在最近 30 筆、還在逐筆追蹤的未完成 run | 依開始時間由新到舊；被靜音或略過的 repo 不顯示 |
| 連結 | 一律以 API 回傳的 `html_url` 為基底 | 只開 `https://github.com/` 開頭的網址，其他不開並寫 error.log |
| GitHub API | 固定送 `X-GitHub-Api-Version: 2026-03-10` | 轉址自己處理，token 只送往 `api.github.com`；一般請求逾時 30 秒、log 下載 120 秒 |
| 視窗 | 預設 1000 × 640、最小 600 × 400、可縮放；記住位置、大小與是否最大化 | 還原時視窗矩形和任何一個螢幕的工作區都不相交（例如原本的螢幕已拔掉），就在主螢幕置中 |
| 開機自啟 | 寫入 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`，值名 `IsItGreenYet`，值是 `"<exe 路徑>" --tray` | 開機時帶 `--tray`，只出現在系統匣、不開視窗；沒有 `--tray` 的舊格式值，在設定頁儲存時改寫。值指向的 exe 已經不存在時（有引號、切得出完整路徑才判斷，UNC 網路路徑不判斷），設定頁顯示未勾選，登錄值不動，勾選並儲存才改寫成目前執行的 exe |

## 資料位置

| 檔案 | 路徑 | 內容 |
|---|---|---|
| 設定 | `%LOCALAPPDATA%\IsItGreenYet\settings.json` | 設定（含介面語言 `language`：`zh-Hant`／`en`、寫入開關 `allowWriteActions`：預設 `false`，以及檢查新版本的開關 `checkForUpdates`：預設 `true`、上次完成檢查的時間 `lastUpdateCheckUtc`、通知過的版本 `lastNotifiedVersion`）、視窗位置、篩選偏好；不含 token |
| 快取 | `%LOCALAPPDATA%\IsItGreenYet\cache.db` | SQLite：登入的帳號（user id、login）、repo 與 run 快照、ETag、靜音與強制納入、通知去重；給命令列讀的狀態表（`status_snapshot`）、repo 的寫入權限、待確認的重跑。時間一律存 UTC |
| API 紀錄 | `%LOCALAPPDATA%\IsItGreenYet\logs\api.log` | 每個請求一行（時間、方法、路徑、狀態碼、剩餘額度、耗時），不記 header 與 body；超過 2 MiB 輪替，保留 3 份舊檔 |
| 錯誤紀錄 | `%LOCALAPPDATA%\IsItGreenYet\error.log` | 未預期例外，超過 512 KiB 輪替成 `.old` |
| PAT | Windows 認證管理員，一般認證 `IsItGreenYet:github.com` | 只有使用 PAT 時才有 |

- `api.log` 與 `error.log` 寫入前會遮掉 token 與 job log 的簽名下載網址。
- `api.log` 的路徑含 repo 名稱，是本機檔案，不要放進版控或分享出去。
- 複製的失敗 log 只放在剪貼簿，不寫入任何檔案。

## 例外處理

| 情境 | 行為 |
|---|---|
| gh 沒裝或沒登入、PAT 失效（401） | 主畫面橫幅（「重新檢查」「開啟設定」）＋系統匣角標，引導執行 `gh auth login` 或到設定貼 PAT（token 來自環境變數時，提示要重新啟動程式）；既有資料不清空；不連續重試。恢復方式見[未登入時](authentication.zh-TW.md#未登入時) |
| 權限不足（不是限流的 403） | 只停那個輪詢目標（例如只停 PR 清單），repo 管理頁與該 repo 的列標示缺的權限；其他目標與其他 repo 照常 |
| 主額度用完 | 全域暫停到額度恢復（用回應的 `Date` 計算，不受本機時鐘影響），橫幅顯示預計恢復時間；暫停最長 70 分鐘（`Tuning.MaxRateLimitWait`），算出來更長時寫 error.log，到期後多送一個請求，還在限流就再暫停 |
| 次級限流 | 有 `retry-after` 就照它暫停（同樣最長 70 分鐘）；沒有就從 60 秒起倍增，上限 16 分鐘；橫幅寫明那是「程式預定重試的時間」 |
| 60 秒內 3 個以上 repo 出現無法分類的 403 | 全域暫停 60 秒一次，寫 error.log |
| 網路中斷 | 保留最後資料，標示「離線 · 最後更新時間」；改用 `GET /rate_limit` 探測，恢復後自動全量刷新；離線期間不發通知 |
| GitHub 持續回 5xx | 角標＋橫幅「GitHub 回應異常」，各目標照退避規則重試 |
| repo 改名 | 以 repo id 跟隨到新名稱，網址用新名稱重組 |
| repo 被刪除（404） | 重抓 repo 清單確認；連續兩輪完整清單都不見才移出；還在清單中就標示並改成每小時重試 |
| repo 沒有任何 workflow | 不顯示在清單；repo 管理頁標示「沒有 workflow（或 Actions 已停用，無法分辨）」 |
| run 狀態為 `waiting`／`requested`／`pending`／`action_required` | 獨立狀態（排隊、等待核准），不算失敗也不算成功 |
| 結論為 `timed_out`、`startup_failure` | 算失敗 |
| 結論為 `cancelled`、`skipped`、`neutral`、`stale` | 不算失敗，灰色 |
| 沒見過的 status | 完成前當「未完成」（黃燈）；完成後結論不認得就歸灰；error.log 記一次 |
| fork 來的 PR（`pull_requests` 為空） | PR 開著時，用開啟中 PR 清單比對（head sha 與來源 repo 都相同）找編號；比對不到就留白，不推測（PR 關閉後的情況見[已知限制第 8 項](known-limitations.zh-TW.md)） |
| 同一個 commit 觸發多個 workflow | 各自一列 |
| 單筆 run 回 404（過了保留期、被刪除） | 只把這筆標成「已不存在」並移出追蹤，保留本地紀錄，不影響 repo |
| GitHub 5xx、422、JSON 格式錯誤 | 只讓該目標退避（上限 10 分鐘，低額度時再乘倍率）；JSON 錯誤時丟棄該筆回應、不更新 ETag；單筆 run 缺欄位時只略過那一筆；都寫 error.log |
| 列表回 204 或空 body | 當成 0 筆 |
| 轉址超過 3 次，或 HTTPS 轉 HTTP | 當成錯誤、不跟隨，寫 error.log |
| API 版本錯誤（400／410） | 停止所有輪詢，加角標，橫幅提示更新程式 |
| 回應帶 `Deprecation`／`Sunset` | 寫 error.log，主畫面提示一次（可以按 ✕ 關閉） |
| job log 拿不到（過期、job 還在跑、簽名網址過期） | 重新取得一次；仍失敗就顯示「拿不到這個 job 的 log（狀態碼 N）」；不影響 repo 狀態 |
| 剪貼簿被佔用 | 每 100 毫秒重試，共 3 次，仍失敗就顯示訊息 |
| 開啟連結的網址不是 `https://github.com/` | 不開，寫 error.log；主畫面另外顯示訊息（提示視窗裡的連結只寫 error.log，見[已知限制第 17 項](known-limitations.zh-TW.md)） |
| 認證管理員讀寫失敗 | 設定頁儲存時：顯示錯誤（含 Windows 錯誤碼），不改變目前的認證方式。啟動或重新檢查時讀取失敗：主畫面只顯示一般的「尚未登入」（見[和設計規格的差異](spec-deviations.md)） |
| `%LOCALAPPDATA%` 不可寫 | 啟動時顯示錯誤並指出路徑 |
| 快取資料庫損毀（啟動時或執行中） | 改名為 `cache.db.corrupt-<時間戳>.bak` 保留，重建空白資料庫；編號備份最多 5 份，滿了改存 `cache.db.corrupt-latest.bak` 並覆寫上一次的這個檔（總共最多 6 份；舊版留下的編號備份也算名額、不會自動清除，所以總量可能更多，要手動刪），程式不刪也不覆寫編號備份。橫幅提示 repo 的靜音與強制納入設定已遺失，有「開啟 repo 管理」，也可以按 ✕ 關閉；主檔已經不在、這次執行也沒有留過備份時，橫幅改說已重建、這次沒有留下備份、設定可能已遺失。改名失敗時：啟動時由 App 的初始化發現的見下一列；監看引擎讀寫時才發現的（啟動時載入資料、建第一份快照，或執行中）見[已知限制第 7 項](known-limitations.zh-TW.md)。改名重建成功、但新的資料庫又讀到損毀時，只留第一份備份，也見[已知限制第 7 項](known-limitations.zh-TW.md) |
| 啟動時無法建立或開啟快取資料庫（損毀以外的錯誤，或發現損毀但改名失敗，例如檔案被別的程式開著） | 寫 error.log，顯示「無法建立或開啟快取資料庫：」加上路徑與原因，按確定後程式結束 |
| 設定檔損毀 | 改名保留，回復成預設值，程式照常啟動；橫幅提示（可以按 ✕ 關閉） |
| 設定檔讀不到、改名也失敗（例如其他程式開著，而且不允許刪除） | 這次用預設值，原檔不動；拒絕寫回（包括設定頁的「儲存」與結束時存視窗位置），免得蓋掉原本的設定；橫幅提示（可以按 ✕ 關閉）並寫 error.log。放開之後重新啟動就恢復。其他程式開著但允許刪除、或只是拒絕讀取時，改得了名，健康的檔案也會走上一列。權限連改名都拒絕（例如拒絕完全控制）時，重新啟動也一樣，所以不拒絕寫回：這次用預設值、只寫 error.log，之後儲存會覆蓋原檔 |
| 重複啟動 | 喚回既有視窗，新行程結束（在程式結束收尾期間再啟動的例外，見[已知限制第 5 項](known-limitations.zh-TW.md)） |
| 系統匣不可用（建立圖示時丟例外） | 降級為一般視窗：帶 `--tray` 也照樣顯示視窗，✕ 直接結束；寫 error.log。沒丟例外、圖示卻沒出現的情況偵測不到（見[已知限制第 1 項](known-limitations.zh-TW.md)） |
| 開機自啟寫入失敗 | 顯示錯誤，這次儲存整個不生效（其他設定也不存），「開機自動啟動」的勾選回到登錄檔的實際狀態 |
| 系統時間被往回調或往前調 | 排程用單調時鐘，不受影響；「未來」的 run 顯示「剛剛」 |
| 未預期例外 | UI 執行緒：寫 error.log、跳對話框、程式繼續執行。背景：寫 error.log，同一種例外 10 分鐘內只用橫幅提示一次，不跳對話框；監看迴圈單輪失敗不會讓迴圈停掉 |
| 寫入：寫入功能關閉時，從別的路徑呼叫到寫入 | 監看引擎回「寫入功能已關閉，沒有送出。」，不送請求 |
