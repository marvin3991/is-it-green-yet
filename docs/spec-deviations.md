# 和設計規格的差異

文中的「已知限制第 N 項」見[已知限制](known-limitations.zh-TW.md)。

程式和[設計規格](specs/2026-10-24-design.md)不一致的地方（最後八點對照的是[第二階段設計規格](specs/2026-10-29-phase2-design.md)），以下是程式的實際行為：

- **`X-GitHub-SSO`（§4.4）**：規格要顯示一次性提示；程式沒有對應的橫幅種類，只寫 error.log 一次。
- **不帶 `If-None-Match` 的請求（§4.1、Q27）**：規格的例外只有 E9（下載 job log）。程式的 E8（job 清單）與 E10（`/rate_limit`）也不帶。E10 要的是當下的額度數字，304 沒有內容可用（程式碼註解），而且 E10 本來就不扣主額度（§4.2）；E8 只在按「複製失敗 log」時送，程式不保存 job 清單的回應，沒有可以比對的 ETag 與內容。
- **取不到 token 的原因（§13.1、§13.3、§15）**：規格要 `ERROR_NO_SUCH_LOGON_SESSION` 等顯示明確的錯誤。程式算出了原因文字，但沒有放進給畫面的快照，所以主畫面與設定頁只顯示一般的未登入；只有在設定頁按「儲存」時重讀並顯示讀取失敗的原因（已知限制第 11 項）。
- **fork PR 的編號（§10.6 第 3 點）**：規格要把第一次觀察到的編號存進 `runs.pr_numbers`。程式只存 API 回傳的 `pull_requests`，靠開啟中 PR 清單比對到的編號沒有存（已知限制第 8 項）。
- **分頁（§4.1）**：E3（workflow 清單）與 E7（開啟中 PR 清單）只抓第 1 頁（`per_page=100`），不跟 `Link` 分頁（已知限制第 9 項）。
- **開機自啟指向已不存在的 exe（§3.3）**：規格只寫以登錄檔的值為準。程式在值有引號、切得出完整路徑而且那個檔案不存在時，當成沒啟用：設定頁顯示未勾選，登錄值不動，勾選並儲存才改寫。沒有引號的舊值切不準路徑，UNC 網路路徑連不上時會卡住畫面，這兩種照舊算已啟用；舊路徑的 exe 還在時的情況見已知限制第 38 項。
- **開機自啟寫入失敗（§11.2、§15）**：規格寫「設定回復為關閉」。程式是勾選回到登錄檔的實際狀態，而且這次儲存整個不生效。新開啟失敗時兩者相同（勾選回到關）；取消開機自啟失敗，或把沒有 `--tray` 的舊格式改寫成新格式失敗時兩者不同：值還在登錄檔，勾選回到開。
- **全量刷新與 workflow 清單（§6.6）**：規格寫全量刷新時 repo 完整清單與 workflow 清單仍依各自的週期。程式對還沒查過 workflow 清單的監看中 repo 改成立即補查一次 workflow 清單，因為有 workflow 才會抓 runs（§5.3）；已經查過的照週期。
- **橫幅的優先順序（§10.2）**：規格寫依嚴重度只顯示最重要的一則。監看引擎的三種一次性提示（API 版本即將停止支援、監看引擎讀寫時發現損毀而重建的快取資料庫復原、未預期錯誤）之間，程式改成較新的優先，同一份快照之前一起發生的才照嚴重度；例如先收到 `Deprecation`、之後才發生未預期錯誤時，顯示的是未預期錯誤。監看引擎只發布選出的那一則，所以較早的那則被蓋住之後，按 ✕ 關掉較新的那則也不會再出現（讀程式推得，未實測）。
- **快取資料庫損毀已復原的橫幅（§10.2）**：規格的動作欄只列「開啟 repo 管理」；程式另外有 ✕ 可以關閉。這是一次性提示，又排在「未預期錯誤」之前，不能關的話，這次執行之後的背景例外提示都出不來。
- **設定檔讀不到又改名失敗（§10.2、§15）**：規格只寫設定檔損毀時改名保留，沒寫改名也失敗的情況。程式這次用預設值、原檔不動，而且拒絕寫回（`SettingsService.LoadFailedFileKept`），另外新增一則橫幅並寫 error.log，放開之後重新啟動就恢復；不這樣做的話，檔案一放開，任何一次儲存都會拿預設值靜默蓋掉設定。持有者允許刪除、或只是拒絕讀取時改得了名，照規格走損毀那條路。權限連改名都拒絕時重新啟動也一樣，拒絕寫回的話設定會永遠存不進去，所以不拒絕：只寫 error.log，之後儲存會覆蓋原檔。
- **快取資料庫持續損毀時的退避（§14.3、§15）**：規格只寫新的資料庫持續讀到損毀時的留檔規則（§14.3），沒寫什麼時候重試；§14.3 的退避指回這一條。程式不會每次都重建：兩次改名重建相隔不到 20 分鐘（`Tuning.RebuildStreakWindow`，錯誤退避上限的兩倍）算連續（中間改名失敗的重試也算，視窗從失敗那次起算），連續 2 次之後再讀到損毀，不管是在寫回、重讀、寫狀態表還是步驟主體讀到的，都改用和改名失敗相同的退避（間隔從 1 秒起倍增，最長 10 分鐘），到了重試的時間才再重建一次；期間的畫面與狀態表見已知限制第 7 項。沒有這個退避時，儲存層持續壞掉會每一步或每個請求重建一次；重試留不留檔見下一條。
- **快取資料庫備份的上限（§14.3、§15）**：規格原本只寫損毀時改名保留，沒有上限，持續損毀時備份會一直累積（第 1 小時 16 份、之後每小時 6 份；用測試替身與假時鐘量到，和退避間隔算出來的 2＋10＋4＝16 相符，未實機測試）。程式的編號備份最多 5 份（`Tuning.MaxCorruptBackups`），滿了改名到 `cache.db.corrupt-latest.bak` 並覆寫，總量最多 6 份（舊版留下的編號備份也算名額、不會自動清除，所以總量可能更多）；程式不刪、不覆寫任何編號備份。持續損毀的重試，這份檔是這個程序自己重建的、之後沒設過靜音或強制納入（寫入失敗不算）、磁碟上至少已有 1 份編號備份、當下用唯讀連線也讀不到 `repo_overrides` 的資料列時，直接刪掉再重建，不留檔（刪之前寫 `error.log`）：這種檔裡只有重抓得回來的快取，以及記憶體裡有、重建時會寫回的資料（完成時通知我、待確認的重跑、帳號）；另外會少掉 `notified`（通知去重紀錄）：這次執行靠記憶體去重；重新啟動後，N1、N2 靠時間界線（§9.3），N3（完成時通知我）不受界線限制，靠通知後取消標記，所以取消標記時又讀到損毀、重抓回來之前就重新啟動時，會多通知一次（用測試替身重現）。其他情況一律改名保留，暫停時也一樣。規格已在 2026-11-02 同步改成這個做法（§14.3、§15），這一點已經不是差異，留給讀過舊版規格的人對照。
- **全域暫停的上限（§6.4 第 1 列）**：規格的公式 `max(retry-after 秒, reset − Date + RateLimitResetMargin)` 沒有上限。程式把所有全域暫停限制在 70 分鐘（`Tuning.MaxRateLimitWait`，設計選擇：1 小時的額度視窗加 10 分鐘餘裕），超過時寫 error.log，到期後多送一個請求，還在限流就再暫停。這是防禦性修改，沒有實際發生過：沒有上限時，異常的 `x-ratelimit-reset`、`retry-after` 或會改寫 `Date` 的中間設備可以讓暫停長達數十年，App 內解除不了，只能重新啟動，橫幅的時間又不帶日期。取捨：如果 GitHub 真的要求等超過 70 分鐘，會提早多送一個請求（是否有這種值沒有驗證）。
- **未登入時不送 API（§13.2、§17）**：離線探測排在認證檢查之前，離線又未登入時，網路恢復會送出 1 個 `/rate_limit`（已知限制第 20 項）。
- **每分鐘請求上限（§6.3）**：設定頁驗證 PAT 的 `GET /user` 不經過監看引擎的節流（已知限制第 21 項）。
- **新增的版面 token（§16.1）**：規格要新樣式只引用既有的 token。顏色確實只引用 `Design.xaml` 的色票；但圓角另外新增了 `Radius.None`（0）、`Radius.RadioButton`（10）與彈出層控制項用的 `Radius.Control`（4），間距與尺寸也在 `Controls.xaml` 的新增區段定義了新的 token（`Margin.*`、`Padding.*`、`Size.*` 等）。介面調整時，`Design.xaml` 另外新增字重 `FontWeight.Emphasis` 與膠囊用的 `Converter.CapsuleRadius`、`Style.Border.Capsule`、`Style.Rectangle.Capsule`，並移除 `Radius.Chip`（規格 §16.1 要新樣式放在 `Controls.xaml`）。
- **錯誤對話框（§15）**：規格寫 UI 執行緒的未預期例外「跳 MessageBox」。程式改用自己的深色對話框（仿 Windows 11 的 ContentDialog，見 `docs/design-notes.md` 的「彈出畫面」）；對話框建立或顯示失敗，或對話框還開著時又發生錯誤，才退回系統 MessageBox。啟動失敗、快取資料庫無法開啟、資料夾開不起來的訊息也走同一個對話框。
- **字型（§16.1）**：規格沿用 SAM 的 `Segoe UI Variable, Microsoft JhengHei UI, Segoe UI`。程式依專案作者指定改成英數用 Consolas、中文用微軟正黑體（`Consolas, Microsoft JhengHei UI`；2026-10-26 中文先用內嵌的霞鶩文楷等寬 TC，2026-10-29 改成微軟正黑體、不內嵌）。原本的 `SemiBold` 與 `Bold` 改用同一個字重 `575`（見[外觀與語言](usage.zh-TW.md#外觀與語言)）。
- **介面語言**：規格沒有這一項。依專案作者要求（2026-10-26）新增英文／繁體中文語言選單，畫面文字集中在 Core 的字串表。
- **彈出畫面的外觀（§16）**：規格只要求沿用 SAM 的視覺。程式另外把系統匣右鍵選單、WPF 的選單與 ToolTip 改成深色，選單、提示視窗與錯誤對話框的外框交給 DWM 畫（圓角、陰影、框線色），提示視窗加上 App 圖示與名稱的標頭，設定頁的「儲存」改成強調色按鈕。
- **排隊時間（§8.2）**：規格寫排隊中的 run 顯示 `now − created_at`。程式改成從 `run_started_at` 算，沒有 `run_started_at` 時才用 `created_at`（2026-10-30 驗收後修正）。理由：重跑時 `created_at` 不會變，照規格算會顯示成從最初建立到現在（驗收時重跑後的列顯示「排隊 33m 30s」）；重跑剛送出、GitHub 還回舊的嘗試的那段時間（已知限制第 29 項），回應裡的 `run_started_at` 已經是這次重跑的時間（實測 1 次），所以不靠 `run_attempt` 判斷。第 1 次嘗試兩者相同（實測 4 次，含 `status: pending` 的 run），顯示和規格一樣。GitHub 如果有時回的是舊的 `run_started_at`，顯示就和修正前相同，不會更差；第 1 次嘗試的 `run_started_at` 如果晚於 `created_at`，排隊時間會少算那一段（推測，沒有看過）。
- **Danger 樣式的兩個寫死顏色（§16.1「不新增任何顏色」）**：第二階段確認對話框的取消類按鈕（「取消這次執行」「強制取消」）照 SAM 原樣使用 `Style.Button.Danger`，滑過與按下時的顏色是寫死的 `#FF9694`、`#E56260`（`Controls.xaml` 的 `Brush.Danger.Hover`、`Brush.Danger.Pressed`），不在色票裡（[第二階段設計規格](specs/2026-10-29-phase2-design.md) D12）。
- **檢查新版本收到限流（§6.4、§9.6）**：規格的限流處理是全域暫停。檢查新版本的請求（E15）收到限流時不全域暫停，只有這個請求最快 1 小時後才重試：需求要求限流時靜默、不影響系統匣的連線問題角標，全域暫停會連帶影響橫幅、角標與所有輪詢。輪詢自己的回應照常處理限流；輪詢已經全域暫停時，到期的檢查不送，算一次嘗試。
- **設定頁最下方不放 GitHub mark（§11.2）**：設定頁最下方原本有 GitHub mark（Invertocat），2026-11-05 作者決定拿掉，只留文字連結，理由是條件最少、之後要加回來容易；§11.2 的表已經照這個決定改寫。原本寫死的 `#FFFFFF`（`Brush.GitHubMark`，§16.1「不新增任何顏色」的例外）也一起移除，所以這裡不再和 §16.1 不一致。
- **發行的 exe（§1.3、§18 第 1 項；第二階段 §10.7、§12、決定 D2）**：規格要一次輸出四個 exe（App 與命令列各有相依框架與自封式），§1.3 也寫「單一執行檔、免安裝」。第一版只發兩個相依框架 exe：`IsItGreenYet.exe`、`IsItGreenYet-cli.exe`。仍是單一執行檔、沒有安裝程式，但使用者要先裝 .NET 10 Desktop Runtime（命令列只需要 .NET 10 Runtime，Desktop Runtime 已包含它），缺 Runtime 時看到的是 .NET 自己的英文提示（見 [README 的系統需求](../README.zh-TW.md#系統需求)與[退出碼表](cli.zh-TW.md#退出碼)）。這是專案作者 2026-11-05 的發行決定，取代第二階段決定 D2 的「兩種都出」；之後要不要再加自封式另外決定。
- **強制取消送出之後（第二階段 §6.4）**：規格只寫取消受理超過 5 分鐘仍未完成時出現「強制取消」，沒寫送出之後。程式在強制取消受理之後，選單不再出現「強制取消」（「取消中」照樣顯示到 run 完成），避免連按兩次送出兩次強制取消。
- **命令列 JSON 的排版（第二階段 §10.3）**：規格的範例是縮排的多行，只是示意。程式輸出一行、不縮排，結尾一個換行，方便腳本處理。
- **命令列 JSON 的時間（第二階段 §10.3）**：和範例一樣是 UTC、結尾 `Z`；範例只有整秒，程式在有小數秒時照寫（最多 7 位、去掉結尾的 0，例如 `2026-10-29T02:00:00.1234567Z`），整秒時連小數點一起省略（`2026-10-29T02:00:00Z`）。
- **設定頁「寫入操作」的說明（第二階段 §9.5）**：規格寫「用 PAT 時要另外開 Actions: Read and write」。程式寫「用 fine-grained PAT 時」：classic PAT 的 `repo` scope 本來就能寫，不用另外開；這樣也和「帳號」卡片的 PAT 說明一致。
- **`--refresh` 提早結束等待（第二階段 §10.5）**：規格只寫等到刷新完成或 210 秒逾時。程式另外在下列任一情況就不再等：送出刷新訊號之後，讀到 App 寫入新的 `stopped_at`（和送出訊號前讀到的不同）；或從送出訊號起已經等了 180 秒（`StatusHeartbeatStale`），期間沒有讀到和送出訊號前不同的心跳（比的是「不同」，不是「較新」：牆鐘往回調時 App 寫的心跳可能比較舊，照樣算 App 有寫）。這兩種情況下 `refreshed` 是 `false`，結果照[退出碼表](cli.zh-TW.md#退出碼)判斷（通常是第 7 列 `app_not_running` 或第 8 列 `stale`），不是 `refresh_timeout`。只看讀得到狀態表的那幾次，暫時讀不到（例如鎖定）時繼續等到逾時。
- **寫入收到 5xx（第二階段 §3.3 第 11 列、§5.2、§9.4）**：規格原本把 5xx 算成「被拒：其他」（對話框說 GitHub 沒有執行），和 §3.2「401 以外的失敗，請求都可能已經生效」矛盾；GitHub 處理太久時也會自己回 5xx。程式照 §3.2 改成「結果不確定」：重跑記成待確認，看到新的嘗試之前兩種重跑都停用、App 重新啟動後接著追；取消照取消的結果不確定處理（不標成取消中、查一次這筆 run）。對話框寫出狀態碼與 GitHub 的訊息，說明可能已經生效，照樣寫 error.log。規格已在 2026-10-30 同步改成這個做法，這一點留給讀過舊版規格的人對照。
- **被拒之後停用寫入的解除時機（第二階段 §4.3）**：規格寫 token 改變時清除。程式在換 token 時只是暫時不套用：換回原本那一把 token 時停用會再生效，要按「檢查連線」（或重新啟動 App）才解除，見[寫入功能需要的權限](authentication.zh-TW.md#寫入功能需要的權限)。
- **授權與第三方聲明的入口（第二階段 §10.1、§10.3；設計規格 §11.2）**：規格的命令列只有 `status` 與 `--help`，設定頁最下方也沒有這個入口。2026-11-05 作者決定把 `LICENSE` 與 `THIRD-PARTY-NOTICES.md` 內嵌進 exe（放在 App、命令列共用的 Core），只下載或轉傳 exe 的人也看得到：設定頁最下方加「授權與第三方聲明」，開對話框顯示全文；命令列加 `notices`，輸出全文，退出碼 0，讀不到或寫入時回報錯誤就是退出碼 4（管線另一端先關閉、stdout 不能寫入時 .NET 不回報，退出碼仍是 0）。`notices` 固定輸出 UTF-8，不是 §10.3 的純 ASCII，因為聲明有非 ASCII 字元；§11.3 的實測裡 UTF-8 在部分接法會亂碼，處理方式見[命令列](cli.zh-TW.md#notices)。`status --json` 不受影響，release 旁的 `LICENSE`、`THIRD-PARTY-NOTICES.md` 照留。這樣算不算隨附、夠不夠，沒有權威來源回答，不確定。
