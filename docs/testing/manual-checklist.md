# 手動測試清單

文中提到的章節：「使用方式」在[使用說明](../usage.zh-TW.md#常用操作)，「fine-grained PAT」在[認證與權限](../authentication.zh-TW.md#fine-grained-pat替代方案)，「例外處理」在[行為、資料位置與例外處理](../behavior.zh-TW.md#例外處理)，「已知限制第 N 項」在[已知限制](../known-limitations.zh-TW.md)。

App 端沒有自動化 UI 測試，下面的項目要在實機上確認。App 請從檔案總管或開機自啟啟動（例外：M23、M40 的 (a) 照步驟從新開的終端機啟動；M29 已經結束檔案總管又要帶 `--tray`，也從終端機啟動；M62 要指定目前目錄，同樣從終端機啟動；M27 的 (d) 要帶環境變數，也從終端機啟動。Windows Terminal 本身也是 MSIX 封裝，會不會導向沒有實測，這幾項優先用傳統主控台視窗；M60 指定的 Windows Terminal 那一次照做，結果和傳統主控台視窗不同時先確認是不是導向），命令列也在同樣的環境執行，不要從 Claude 桌面 App 這類 MSIX 封裝的程式啟動：那樣讀寫的會是另一份資料（[已知限制](../known-limitations.zh-TW.md)第 36 項，[實機驗收紀錄](acceptance.md#測試環境msix-檔案導向)）。2026-10-30～31 的結果見[第一階段的手動測試](acceptance.md#第一階段的手動測試)。M1～M13 來自設計規格 §18.1；M14～M52 是實作後補上、開發時沒辦法自動驗證的項目；M53～M60 來自[第二階段設計規格](../specs/2026-10-29-phase2-design.md) §16.3，2026-10-30 的實機結果見[第二階段的實測結果](acceptance.md#第二階段的實測結果)。M61～M63 是 2026-11-03 代碼審查之後補上的項目。M64、M65 要等公開並發佈第一個非 prerelease 的 release 之後才能做。M66 是檢查新版本的設定頁畫面，不必等公開。M61～M63、M66 的結果見[之後補上的手動測試](acceptance.md#之後補上的手動測試)。M54～M59 要開啟寫入功能，按錯就會真的重跑或取消 run（M56、M58 一定會送出），用可以隨意重跑的測試 repo，不要用正式的 repo。會改到系統狀態的步驟（登出 gh、刪除 PAT、搬走資料夾、改壞 `cache.db` 或 `settings.json`、改登錄檔的開機自啟值、結束 `explorer.exe`），先備份，測完改回原狀。

M53、M55、M57 要確認「從某個時間點起沒有送出 POST」：`api*.log` 會保留之前的紀錄（例如 M56 一定會送出的 POST），所以只看那個時間點之後的行。在同一個 PowerShell（pwsh 7 或 Windows PowerShell 5.1）裡先記下開始時間，做完步驟後列出之後的 POST 行，沒有輸出就是沒有：

```powershell
# 開始之前
$start = [DateTimeOffset]::Now

# 做完步驟之後：列出 $start 之後的 POST 行（api.log 第一欄是時間、第二欄是方法，Tab 分隔）
Get-Content "$env:LOCALAPPDATA\IsItGreenYet\logs\api*.log" | Where-Object {
    $fields = $_ -split "`t"
    $fields.Count -gt 1 -and $fields[1] -eq 'POST' -and [DateTimeOffset]::Parse($fields[0], [cultureinfo]::InvariantCulture) -ge $start
}
```

下面幾個待驗證的項目沒有列成步驟，因為沒有安全的重現方式：

- 開機自啟寫入登錄檔失敗時的顯示：要改 Run 機碼的權限才能製造，會影響其他程式的開機自啟。設定頁的處理（顯示錯誤、勾選回到實際狀態、什麼都不存）用測試殼的假寫入驗過。
- UI 執行緒未預期例外的對話框：目前沒有不改程式就能觸發的已知方法。對話框本身（外觀、owner 與置中、長訊息捲動、對話框開著時又出錯或建立失敗時退回系統 MessageBox）用測試殼以假訊息驗過；實機按鍵見 M42。長到出現捲軸的訊息只有這種例外會產生（M33、M41 的訊息都只有幾行），所以錯誤對話框的 `Ctrl+Home`／`Ctrl+End` 與 `Shift` 加方向鍵延伸選取，實機還做不出來；`↑`／`↓`、`PageUp`／`PageDown`、`Home`／`End` 用測試殼驗過，這兩組修飾鍵只讀過程式（測試殼送不出修飾鍵）。
- 「未預期錯誤」橫幅的「開啟資料夾」：要先出現背景的未預期例外，目前沒有安全、不改程式就能製造的方法。這個按鈕和系統匣、設定頁的「開啟資料夾」呼叫同一個方法（`WindowNavigator.OpenDataFolder`），M34 驗的是後兩者。
- 兩則可以關閉的橫幅同時出現時，按 ✕ 關掉一則後改顯示下一則：可以關閉的只有 API 版本即將停止支援、快取資料庫復原、設定檔復原、未預期錯誤四種，而且都排在其他橫幅之後，所以要這四種裡同時出現兩則。API 版本即將停止支援與未預期錯誤沒有不改程式就能觸發的方法；啟動時 `cache.db` 與 `settings.json` 都損毀時，App 只保留資料庫那一則；要讓資料庫復原和設定檔復原同時出現，得另外做出只有監看引擎讀寫時才發現損毀的 `cache.db`（檔頭正常、損毀在資料裡）。只讀過程式。
- GitHub 持續回 5xx 時橫幅的「立即重試」：沒辦法讓 GitHub 回 5xx。Core 的單元測試用假的 5xx 回應驗過這則橫幅會出現、恢復後會消失；「立即重試」和離線橫幅（M1）是同一個按鈕、同一個處理常式（全量刷新）。
- 實際 SQLite 下輪詢與使用者操作同時存取資料庫（例如開設定頁時從 `cache.db` 讀目前登入的帳號）：沒有做並行壓力測試，也沒有能讓兩者剛好同時發生的方法，只能靠 M38 長時間執行間接觀察。
- 真實的網路逾時（一般請求 30 秒、log 下載 120 秒）：要有能讓連線卡住、不回應的網路環境。單元測試用不回應的假傳輸層加上可控的時鐘，驗過逾時會當成網路錯誤；真實的連線失敗由 M1 的停用網卡涵蓋一種。
- 真實 API 的 404（repo 被刪除）：沒辦法在不動使用者 repo 的情況下讓 GitHub 回這個狀態碼。單元測試用假回應驗過連續兩輪不見才移除；「例外處理」表的 repo 被刪除、`waiting` 狀態這幾列，都還沒用真實 API 驗證過；fork 來的 PR 與 `completed`＋`action_required` 只讀過公開 repo 的回應（見[第一階段的驗收](acceptance.md#第一階段的驗收)），沒有看過 App 的畫面。301（repo 改名）已在第二階段驗收時用 private 沙盒 repo 實測，App 跟隨到新名稱（見[第二階段的實測結果](acceptance.md#第二階段的實測結果)的 R15）。
- 設計規格 §18 另列的實測：沒有另外建沙盒，fork PR 的 run 欄位（`head_branch`、`pull_requests`、`head_repository`）與待核准 run 的 status／conclusion 改讀公開 repo 的回應，見[第一階段的驗收](acceptance.md#第一階段的驗收)。repo 改名後 API 的回應已實測（同上）。
