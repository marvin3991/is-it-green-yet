## 第一階段的驗收

第一階段的驗收（[設計規格](../specs/2026-10-24-design.md) §18，2026-10-26）：

- 第 1 項：Core 有 1,207 個單元測試全部通過；`tools/publish.ps1` 先跑測試，再輸出兩個執行檔（當時是 `3,207,327` 與 `157,785,153` bytes；目前的大小見[自行建置](../building.zh-TW.md#兩個執行檔)）。
- 第 2 項：用真實帳號挑 2 個 repo，各 10 筆 run 和 GitHub 逐筆比對狀態、標題、分支、觸發者、開始時間、耗時與順序，0 筆不一致；另挑 3 筆比對耗時，差距 0 秒（標準 ≤ 5 秒）。比對表含私人 repo 內容，依規格不進版控。
- 第 4 項：發佈版執行 1 小時（04:47:56～05:47:56），`api.log` 共 317 個請求（每分鐘 5.28；扣掉前 5 分鐘的啟動期是 5.07），304 佔 315 個（99.4%），只有 `/user` 與 `/rate_limit` 各回一次 200；E5（預設分支補抓）2 次都回 304；各端點每分鐘：push 探測 1.95、runs 2.4、workflow 清單 0.45、開啟中 PR 0.4，和 §6.7 的估算（平常每分鐘 5.0～6.5）一致。這 1 小時沒有 run 在跑；「job 推進期間 runs 列表是否維持 304」在第 3 項的測試 PR 期間觀察到：維持 304（見下一項）。這次用的執行檔是最後兩個修正（結束時寫入佇列裡的選擇、資料庫復原橫幅可關閉）之前的建置，兩者都不影響請求。
- 第 3 項：在本 repo 加上只做建置與測試的 CI（`.github/workflows/ci.yml`），用新增它的 PR（#3，目標分支 feat/phase1）觸發 CI，發佈版 App 開著觀察。CI 在 14:47:10 建立，App 14:47:24 顯示「1 進行中」與這一列（「進行中 · 已執行 …」每秒更新）；14:49:24 完成（成功），App 14:49:37 改成「0 進行中」、這一列「成功 · 2m 14s」（和 GitHub 的耗時一致），14:49:43 跳出提示「成功：（本 repo 當時的完整名稱）· CI #1」，約 5 秒後自動消失。PR #3 合併進 feat/phase1 後，PR #2 的 CI（2m 47s）也一樣：進行中、轉綠、提示都正確。`api.log`：push 探測一偵測到 push，立即查 workflow 清單（只在 PR 分支上的 workflow 也列得出來）、runs、開啟中 PR；job 推進期間 runs 列表每 15 秒一次、全部 304；完成時回 200，之後回到 30 秒的安靜間隔。系統匣圖示收在「隱藏的圖示」區，沒有直接看圖示本身：系統匣與摘要列用同一份快照、同一套整體狀態判斷，由摘要列的「1 進行中 → 0 進行中、0 失敗」推得系統匣由黃轉綠（實際外觀列在手動測試 M6、M36）。
- 第 5 項的[手動測試清單](manual-checklist.md)：2026-10-30～31 做了不需要專案作者在場的部分，見下一節。
- §18 另列的實測：repo 改名後的 API 回應已在第二階段驗收時實測（見[第二階段的實測結果](#第二階段的實測結果)的 R15）。另外兩項沒有建沙盒，2026-11-05 改讀公開 repo 的 API 回應（`GET /repos/{owner}/{repo}/actions/runs`），樣本都很少：
  - fork PR 的 run：`dotnet/runtime` 最近 50 筆成功的 run 有 15 筆 `head_repository.fork` 是 true。看其中 2 筆（event 是 `pull_request_target`）：`pull_requests` 是空的，`head_branch` 有值。對照是 `cli/cli` 同 repo 的 PR 1 筆，`pull_requests` 有 1 個。
  - 待核准的 run：`microsoft/vscode` 的 `status=action_required` 看 5 筆（2 個分支，都來自 fork，event 是 `pull_request`）：`status` 是 `completed`，`conclusion` 是 `action_required`，`pull_requests` 是空的。`RunStateMapper` 把這個結論當成等待核准。`status=waiting` 查 `cli/cli`、`dotnet/runtime`、`microsoft/vscode` 都是 0 筆，所以沒看到這個狀態的欄位。
  - 沒驗證：App 面對這些 run 的實際畫面，只有單元測試。

App 端沒有自動化 UI 測試（§17），畫面與 Windows 整合的行為要照手動測試清單在實機確認。

## 第二階段的實測結果

2026-10-30 的實機驗收，對應[第二階段設計規格](../specs/2026-10-29-phase2-design.md) §16.2 的 R1～R15 與手動測試 M53～M60。App 是 `830ec54` 的發佈版（`830ec54` 是 PR #6 分支上的 commit，PR #6 以 squash 合併成 main 的 `c37402d`；兩者建置出的四個執行檔大小相同），用真實帳號執行（之後的修正見[和設計規格的差異](../spec-deviations.md)的「排隊時間」；PR #8、#10～#15 與 2026-11-03 的第一次載入修正也改了監看引擎，沒有用新版重測的紀錄）。寫入都對 private 沙盒 repo（名稱不寫進 repo；`Sandbox` workflow 見第二階段設計規格 §16.1）。每一批寫入（觸發、重跑、取消、改 workflow 檔、停用 workflow、改名）都在執行前經專案作者同意；其中一批原本只打算用 `gh api` 送 1 個取消，實際送出 2 個，這筆 run 的取消總數仍是同意的 2 個（見 R5、R7）。測完沙盒的 workflow 檔、workflow 的啟用狀態、repo 名稱，以及 App 的寫入開關、認證方式與語言都已還原。

- 除非另外寫出次數，每一項都只做了 1 次（n=1）。
- 秒數是 `api.log` 的時間與 GitHub 回應裡的時間相減。
- 「用 `gh api`」是不經過 App、直接對 GitHub 送請求：App 做不到、或這次沒機會由 App 送的項目才這樣做，表裡寫明。
- 結果欄的判定：規格要查的事都有答案、[手動測試清單](manual-checklist.md)那一項的步驟都做了而且有紀錄，才是「通過」。只要有一個步驟沒做或沒有紀錄，或規格要查的事有一部分沒有答案，就是「部分通過」，並寫出缺的部分（「缺：」）。設想的情況根本沒有做出來的是「沒有照設想走到」，表裡寫改測了什麼。R 項沒有手動測試清單的步驟，對照第二階段設計規格 §16.2 的「要查清楚的事」與「做法」。2026-10-30 時，23 項裡通過 7 項、部分通過 14 項、沒有照設想走到 2 項；2026-10-31 補測 R6（強制取消）後，R6、R11、M59 改判通過，變成通過 10、部分通過 12、沒有照設想走到 1（R13）。
- 標「（讀程式推得）」的是沒有實際看到、從程式推得的部分；引用的畫面文字和驗收紀錄不同時，寫明以程式為準。

### 資料庫損毀改名

R12 的最後一項。結束 App、備份之後把 `cache.db` 前 100 bytes（SQLite 檔頭）蓋成亂碼，命令列在迴圈裡執行時啟動 App。測完從備份還原，`cache.db`、`cache.db-wal`、`cache.db-shm`、`settings.json`、`error.log` 的 SHA256 都和備份相同。

> 2026-10-31 補充：這一段的 App 與命令列都是從 Claude 桌面 App 的工作階段啟動的，受 [MSIX 檔案導向](#測試環境msix-檔案導向)影響。依 2026-10-31 的重現實驗推得：壞檔改名後，SQLite 開同一路徑時落到實體位置另一份 10/26～27 的舊 `cache.db`，所以下面說的「重建」其實是打開那份舊檔、補上缺的表，不是建一份空白的資料庫。改名與重新抓資料的行為不受影響。空白重建在 2026-10-31 於封裝環境外重做過（[第一階段的手動測試](#第一階段的手動測試) M26、M41）；命令列在重建期間迴圈讀取的部分沒有在封裝環境外重做。

- 只蓋掉 `cache.db` 的檔頭：`cache.db-wal` 裡有第 1 頁，SQLite 照樣讀得到，App 與命令列都正常，沒有判定成損毀。
- App 結束後把 `cache.db` 與 `cache.db-wal` 的檔頭都蓋掉：命令列立刻回 4 `db_error`（stderr 英文一行），沒有建立或改名任何檔案。
- 命令列每 100 毫秒執行一次（2 分鐘共 359 次）的期間啟動 App：不到 1 秒就把壞檔改名成 `cache.db.corrupt-<時間戳>.bak` 並重建，error.log 沒有新紀錄；重建後 16 張表，重新抓到 repo 清單與權限，狀態表有寫。命令列依序回 4 `db_error` → 3 `no_status`（App 啟動後約 0.7 秒）→ 4 `data_stale`（約 2.4 秒，已知限制第 33 項）→ 0（約 3.4 秒）。改名沒有被命令列的唯讀連線擋住（n=1）。
- 重建後的 `cache.db` 在檔案總管顯示的建立時間是 10/26、修改時間是 10/27，不是當下。原因（2026-10-31 重現，套到這次是推得）：上面補充說的 MSIX 導向，「重建」開到的是實體位置那份舊檔；WAL 模式下主檔要到檢查點才寫入，修改時間停在 10/27。另外，NTFS 的檔案系統通道會讓 15 秒內在同一資料夾重建的同名檔沿用舊檔的建立時間（修改時間不會），所以一般環境下重建後的建立時間也會是舊的。程式不讀檔案時間，資料新舊看的是資料庫內容（狀態表的寫入時間與心跳），不受影響；要知道什麼時候重建的，看 `.bak` 檔名裡的時間戳。

### 其他觀察

- 手動觸發的 run 在安靜的 repo 不會馬上出現在 App（間隔最長 300 秒，同[行為規格](../behavior.zh-TW.md#行為規格)的「新 run 出現的時間」）；驗收時用命令列 `--refresh` 叫 App 刷新。

## 測試環境：MSIX 檔案導向

2026-10-30 做第一階段手動測試時發現：從 MSIX 封裝的程式（這次是 Claude 桌面 App）啟動的行程，看到的 `%LOCALAPPDATA%` 會被 Windows 導向該套件的私有位置（`%LOCALAPPDATA%\Packages\<套件>\LocalCache\Local\`）。所以：

- 從 Claude 桌面 App 啟動的 IsItGreenYet，讀寫的是 `…\LocalCache\Local\IsItGreenYet`；從檔案總管或開機自啟啟動的，讀寫真正的 `%LOCALAPPDATA%\IsItGreenYet`。兩份資料互不相干。設定頁「資料」卡片顯示的路徑一樣是 `%LOCALAPPDATA%\IsItGreenYet`（封裝環境外實測），看不出差別；從封裝環境啟動時，「開啟資料夾」交給檔案總管開，看到的可能是真正位置那一份（推得，沒有實測）。
- 命令列也一樣：要和 App 用同一種方式啟動，否則讀到的是另一份 `cache.db`。
- 兩份都有同名的檔案時，改名或刪除其中一份之後，同一個路徑可能落到另一份（[資料庫損毀改名](#資料庫損毀改名)的補充）。
- 第二階段驗收（R1～R15、M53～M60）與第一階段手動測試的畫面類項目都是在這個環境下做的。它們只讀寫同一份資料，結果不受影響（推得）；要改資料夾或檔案的項目在 2026-10-31 改到封裝環境外做。
- 其他封裝程式（例如從 Windows Terminal 啟動）會不會這樣，沒有實測。
- 對使用者的影響記在[已知限制](../known-limitations.zh-TW.md)第 36 項。
