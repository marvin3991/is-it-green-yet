# 已知限制

[English](known-limitations.md) | 繁體中文

回到 [README](../README.zh-TW.md)。

下面的問題都不會連續送出無效憑證。第 1～28 項的影響都是「低」（要特定時機或少見的條件才會發生，或只影響顯示），依影響由大到小排列。第 29～46 項接在最後，沒有和前面一起排序，影響寫在各項「會怎樣」欄的最後。標「未實測」的是讀程式推得、沒有實際重現，標「推測」的是連會不會發生都還沒確認；「實測 1 次」是只觀察過一次（n=1）。

測試範圍：在 Windows 11 x64 上測試。以一般（未提升）權限執行還沒有測過；exe 本身依設計不需要系統管理員權限，安裝 .NET Runtime 可能需要（見 [README 的系統需求](../README.zh-TW.md#系統需求)）。

| 4 | 主視窗收在系統匣時從系統匣開設定頁，再從系統匣叫出主視窗切換「置頂」，之後在設定頁按「儲存」（完整流程未實測） | 置頂被改回設定頁開啟當時的值 | 要改置頂就在設定頁改；或先關掉設定頁再按主畫面的置頂鈕 |

| 6 | 程式執行中 `cache.db` 損毀、被改名重建 | 已經不在最近 30 筆、被標記「完成時通知我」的進行中 run 不再更新：完成時不通知、主清單少了這一列，標記留在資料庫裡。重新啟動也一樣：啟動和重建都是從資料庫載入，新的資料庫沒有這筆 run（重新啟動的部分未實測）。剛打開「包含協作 repo」、協作 repo 清單還沒抓完就重建時，打開設定之前已經完成的協作 repo 失敗會多發一次通知 | 重新啟動不會恢復；只有這筆 run 剛好又被其他輪詢抓回來（預設分支或 PR 分支的補抓）時才恢復，否則完成時不會通知，要到 GitHub 網頁看結果。清單上沒有這一列，也沒辦法重新標記 |
| 7 | `cache.db` 的檔頭正常、損毀在資料裡（啟動時 App 的初始化沒發現，監看引擎讀寫時才發現），而且改名重建失敗（例如另一個程式長時間開著 `cache.db`）。依發現的時機分三種：(a) 啟動時監看引擎載入 repo、run 等資料就讀到損毀；(b) 載入成功，建第一份快照時才讀到；(c) 執行中、已經發布過資料之後才發現。三種都是讀程式推得，未實測。啟動時 App repo）」，計數、repo 清單與「最後更新」時間都停在第一份；狀態是灰色（無資料），有「未預期錯誤」橫幅；輪詢與寫入照常。(c) 清單、計數與狀態顏色停在改名失敗前的最後一份（不是空的），摘要列的「最後更新」與 tooltip 的「更新於」也停在那個時間，離線與 5xx 橫幅的時間照常更新，角標照常更新，有「未預期錯誤」橫幅；輪詢照常。三種都在背景重試改名，間隔從 1 秒起倍增，最長 10 分鐘一次。改名重建成功、新的資料庫又讀到損毀時：20 分鐘內改名重建 2 次之後，再讀到損毀就改用和改名失敗相同的退避，間隔從 1 秒起倍增，最長 10 分鐘。退避期間清單與「最後更新」停在沿用的那份快照，可能是重建後的空清單（重試時可能換上重建後新組的一份），也可能是損毀前的最後一份；沿用的是清單抓完之前組的空清單時，清單區與 repo 管理停在「正在載入」，即使清單其實已經抓回來，也不會說「目前沒有 workflow 執行紀錄。」或「沒有看得到的 repo。」（看得到的 repo 真的是 0 個時也一樣，要等儲存層恢復）；狀態表不寫，所以命令列的結果看損毀在哪裡：狀態表本身壞掉時是 4 `db_error`；其他的表在重建的那一步就讀到損毀時，新的資料庫沒有狀態列，回 3 `no_status`；撐過重建那一步才讀到時，照最後寫入的那一列判斷（例如 `overall` 對應的 0／1／2、3 `no_data` 或 4 `data_stale`），心跳超過 180 秒後回 4 `stale`，這時 App 其實還在執行；下一次重試重建後可能又寫入新的一列，結果會來回變動。輪詢繼續排程，但請求常比平常少（`http_cache` 壞掉時送不出去），每次重建後又像冷啟動一樣重抓，那時請求可能比平常多。使用者的指令下一步就處理，但清單與 repo 管理要到下一次重試才反映（暫停中會重新抓清單的操作除外：`F5`、開啟 repo 管理、改「包含協作 repo」或「包含 fork」，見右欄）；指令要寫的表也壞掉（靜音或強制納入見第 24 項），或畫面上的 run 是重建前沿用下來的時候，這次操作不會生效；這段期間設的靜音與強制納入，在重試重建時遺失（寫入成功的話，內容留在那次多留的備份裡）。例外：啟動時載入資料就讀到損毀、還沒初始化完成時，和 (a) 一樣清單區停在「正在載入」、不取 token、不輪詢，指令要等初始化完成才套用。這些情況的橫幅都是資料庫復原的那一則（「快取資料庫無法讀取，已改名保留為…」，檔名是這次執行最後留下的那份；一份都沒留過時改說已重建、這次沒有留下備份），不是「未預期錯誤」，每次重試都換一則新的，按 ✕ 關掉後下一次又會出現。持續損毀只留第一份 `cache.db.corrupt-*.bak`，重試照常但不多留檔，按暫停時也一樣（這段期間又成功寫入靜音或強制納入時，下一次重試多留一份，寫入失敗不算）；編號備份最多 5 份（舊版留下的也算），滿了存 `cache.db.corrupt-latest.bak` 並覆寫，程式不刪編號備份；持續損毀期間每次重新啟動可能多留 1～2 份，直到滿額 | 關掉開著 `cache.db` 的程式；改名重建成功後自動恢復（暫停中清單不會自己回來，做法見本欄後面的暫停說明），(b)(c) 重建後的情況同第 6 項。改名重建成功、新的資料庫又讀到損毀時：檢查磁碟；儲存層恢復後，執行中最晚 10 分鐘內下一次重試就自動恢復（啟動時載入資料就讀到損毀的情況可能更久：改名重建之後還要等下一次載入重試），之後同第 6 項；暫停中也一樣，不必解除暫停或重開 App，只是暫停期間不輪詢，清單區停在「正在載入」，要自己重新抓：儲存層恢復後，等下一次重試重建（最晚 10 分鐘；沒按過 ✕ 時畫面通常看不出來，直接等滿最保險；想確認的話先按 ✕ 關掉橫幅，重試時它會再出現）再按 `F5` 或開啟 repo 管理；更早重新抓的結果（包括改「包含協作 repo」或「包含 fork」）會被那次重建清掉，要再按一次 `F5`，或關掉 repo 管理重開（啟動時載入資料就讀到損毀、還沒初始化完成時例外：指令留到初始化完成才套用，不會被清）。解除暫停不必等，恢復後下一次重試重建完會自動重抓完整清單。重建之後第一次按 `F5` 抓完整清單（開著「包含協作 repo」時是兩份），再查各 repo；全部查完之前，看得到的全部成功時總狀態是灰色（無資料，命令列是 `no_data`），失敗與進行中照常顯示，看得到的 repo 是 0 個時仍是「正在載入」。清單抓到一半失敗時不會自動重試（被限流時例外：全域暫停結束後自己重抓），已抓到的分頁照常顯示、總狀態一樣是灰色，再按一次 `F5` 或解除暫停就補齊（清單回 403／404 時要等 1 小時的重試間隔，這段期間按 `F5` 只送探測）；這時如果先重新啟動，會分不出清單不完整，總狀態可能是綠色，第一次 `F5` 補齊之後才對。等重試重建的期間按 `F5` 只送探測，不抓完整清單。多出來的 `.bak` 可以手動刪除，連同同名的 `-wal`、`-shm`、`-journal` 一起刪；要刪時看修改日期而不是檔名，不確定就先複製到別處。要把備份改名回 `cache.db` 救設定之前，先結束 App |
