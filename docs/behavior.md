## Behavior

| Item | Description | Range / limits |
|---|---|---|
| Monitoring scope | By default, monitors your own repos and your organizations' repos; forks and collaborator repos are skipped by default and can be turned on in Settings | Skipped automatically: muted, archived, disabled, fork, collaborator, no activity for over 90 days (and no local run within 90 days), no workflows, all workflows disabled. Archived, disabled, no workflows, and all workflows disabled can't be force included |
| Polling (Auto mode) | Each repo is scheduled separately, and polling requests send `If-None-Match` (ETag); separately, a probe every 30 seconds checks which repos were just pushed to | With a run in progress: 15 seconds; when quiet: seconds since the last activity ÷ 30, clamped to 30–300 seconds; at least 300 seconds while the screen is locked. When you choose a fixed interval, that interval is used instead; see "Adjust auto-refresh" in [Usage](usage.md) |
| When new runs appear (Auto mode) | Runs triggered by a push appear within about 30 seconds of being created | For 15 minutes after a push, that repo is polled every 30 seconds. Scheduled runs, manual triggers, and re-runs don't change the push time and rely on the repo's own polling, so for a quiet repo they can be up to 5 minutes late |
| Lock, sleep, wake | While locked, all intervals are at least 300 seconds and notifications are held; no requests are sent during sleep | A full refresh runs immediately after unlocking, waking, or coming back online. Besides Windows' wake event, a gap of more than 120 seconds between two consecutive once-per-second ticks also counts as having just woken (inferred, not tested: an unattended wake may not raise a wake event). A full refresh makes the push probe and the runs and PR list of every monitored repo due immediately; they still send ETags and stay under the per-minute cap. Targets waiting to retry after a permission error or 404 aren't moved up. The full repo list and the workflow lists keep their normal schedule, except for monitored repos whose workflow list hasn't been fetched yet: their workflow list is fetched once right away, and only if they have workflows are their runs and PR list fetched next. While paused, if the app hasn't finished fetching the full repo list yet (for example, the database was just rebuilt, or the app started paused), a full refresh fetches the full list instead of sending the push probe; while the list is waiting to retry after a 403 or 404, or during the database rebuild backoff, it sends the probe as before |
| API quota | Shared with gh and other tools: 5,000 requests per hour | A 304 doesn't count against the primary quota. Polling sends only one request at a time (a separate lane handles copying logs and writes), at most 60 per minute. When less than 25% remains, all intervals are stretched 2–8× |
| Writes (re-run, cancel) | A `POST` is sent only when write actions are on and you click the action button in the confirmation dialog; no body is sent, no ETag is sent, and the cache isn't read or written | At least 1 second between two writes, and writes count toward the 60 per minute. A write that waits in the queue for more than 15 seconds is dropped (not sent). Not sent while signed out, on an API version error, while paused by rate limiting, or while offline (still sent when auto-refresh is "Paused"). Redirects are never followed. No automatic resend; the only exception is one resend after a 401 when a new token is obtained. A 5xx from GitHub may already have taken effect, so it counts as an uncertain result, not a rejection. After sending (including rejected and uncertain results), the run is checked once right away. A re-run is tracked until a new attempt appears or the run becomes not completed (gives up if it still isn't seen after more than 5 minutes and 3 checks; if only "not completed" is seen, see item 29 in [Known limitations](known-limitations.md)). An accepted cancellation is tracked until the run completes |
| Tracked runs (decide the tray color) | The latest run of each workflow on the default branch, plus the latest run for each open PR branch × each workflow | An older failure stops counting only when a newer success replaces it; cancelled or skipped runs don't replace a failure. A PR is no longer tracked after it's closed. Failures older than 90 days don't count. Disabled workflows aren't tracked. For a key that counts as failing, the newest failed run of its last result is checked once an hour when it isn't among the latest 30, and stops counting once it's deleted on GitHub (not checked while auto refresh is paused) |
| Overall state | Failed > in progress or queued (including waiting for approval) > all succeeded > no data | Tracked items whose conclusion is only cancelled or skipped neither turn the state green nor block green. Connection problems are shown as an overlaid badge and don't change the color |
| Notifications | A tracked run fails; a run you triggered (`actor` is you) succeeds; a run you marked "Notify me" finishes; for a run re-run in the app, the new attempt finishes (automatically treated as "Notify me") | The three can be turned off separately (notifications after a re-run follow the **Notify when a run marked "Notify me" finishes** setting). The same attempt and conclusion of a run is notified only once, and not again after a restart. Runs that finished before the app started aren't notified ("Notify me" is the exception). Notifications within 2 seconds are combined into one |
| Notification window | A custom window in the bottom-right corner of the primary screen's work area (16 DIP from the edges), always on top, doesn't take focus, and doesn't appear in the taskbar | Failures stay for 12 seconds (3–120), successes and gray conclusions for 5 seconds (2–60); the timer pauses while the mouse is over it. The title of a summary notification is "N runs changed (X failed, Y succeeded, Z other)" (counts of 0 are left out), listing at most 5 lines, with the rest shown as "N more"; for click behavior, see [Usage](usage.md). While locked, notifications are held, and after unlocking they're combined into one "Changes while locked". Windows system notifications aren't used (Focus assist would swallow them) |
| Check for new versions | When the last completed check is at least 3 days old, or there hasn't been one, asks GitHub for this project's latest release with your token (`GET /repos/marvin3991/is-it-green-yet/releases/latest`). If it's newer than the running version (compared by SemVer, without the tag's `v` or the running version's build metadata), a notification pops up, and clicking it opens that release's page. It only notifies: the app never downloads or replaces itself. On by default; after you turn off "Check for new versions every 3 days" in Settings, this request is never sent | Whether it's due goes by the UTC wall clock, decided locally (without connecting) once an hour, and also after sign-in is verified (including at startup), waking, and unlocking; a last check time in the future counts as due. 200, 304, and 404 count as completed. After a failure, or when it comes due while offline, paused by rate limiting, or on an API version error, it retries no sooner than 1 hour later (the network often isn't up yet right after waking, so this can happen then). Skipped while signed out and during sleep. Auto-refresh being "Paused" doesn't stop this check. It sends an ETag only after a check has completed; it uses the polling lane and counts toward the 60 per minute, but its response doesn't update the quota or "Last updated". The same version is notified only once, and not again after a restart; the three notification settings don't apply to it, and it stays as long as a failure notification (12 seconds by default). `/releases/latest` never returns prereleases or drafts, so those are never notified. If you turn the option off while a request is in flight, the result is discarded; after you turn it back on, it picks up within 1 hour at most |
| Duration | `updated_at − run_started_at` | GitHub doesn't officially define the meaning of these two fields, so this is an inference |
| Estimated time remaining | The median duration of the last 10 successful runs of the same workflow in the same repo | Only first-attempt successes count (successful re-runs don't; re-running only the failed jobs usually takes less time). No estimate with fewer than 3. Shown as "~Nm left" (rounded up to the minute); once exceeded, shown as "~Nm over estimate" |
| Start time | Always in the local time zone | Just now (within 60 seconds, or clock skew) / N min ago / Today HH:mm / MMM d HH:mm / MMM d, yyyy |
| List contents | The latest 30 runs of each monitored repo, plus tracked runs, runs marked "Notify me", and incomplete runs outside the latest 30 that are still being tracked one by one | Sorted by start time, newest first; muted or skipped repos aren't shown |
| Links | Always based on the `html_url` returned by the API | Only URLs starting with `https://github.com/` are opened; others aren't opened and are written to error.log |
| GitHub API | Always sends `X-GitHub-Api-Version: 2026-03-10` | Redirects are handled by the app itself, and the token is sent only to `api.github.com`. Timeouts: 30 seconds for normal requests, 120 seconds for log downloads |
| Window | Default 1000 × 640, minimum 600 × 400, resizable; remembers position, size, and whether it was maximized | If, on restore, the window rectangle doesn't intersect the work area of any screen (for example, the original monitor was unplugged), it's centered on the primary screen |
| Start with Windows | Writes to `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, value name `IsItGreenYet`, value `"<exe path>" --tray` | At startup it runs with `--tray`, so it appears only in the tray and doesn't open a window. An old-format value without `--tray` is rewritten when you save in Settings. If the value points to an exe that no longer exists (checked only when it's quoted and has a full path, and not for UNC network paths), Settings shows the box unchecked and leaves the value alone; checking the box and saving rewrites it to the exe that's running |

## Data locations

| File | Path | Contents |
|---|---|---|
| Settings | `%LOCALAPPDATA%\IsItGreenYet\settings.json` | Settings (including the interface language `language`: `zh-Hant`/`en`, the write switch `allowWriteActions`: default `false`, and for checking for new versions the switch `checkForUpdates`: default `true`, the time of the last completed check `lastUpdateCheckUtc`, and the version last notified about `lastNotifiedVersion`), window position, filter preferences; no token |
| Cache | `%LOCALAPPDATA%\IsItGreenYet\cache.db` | SQLite: the signed-in account (user id, login), repo and run snapshots, ETags, mute and force-include settings, notification deduplication; the status table read by the command line (`status_snapshot`), per-repo write permission, and re-runs awaiting confirmation. All times are stored in UTC |
| API log | `%LOCALAPPDATA%\IsItGreenYet\logs\api.log` | One line per request (time, method, path, status code, remaining quota, duration); headers and bodies aren't logged. Rotated after 2 MiB, keeping 3 old files |
| Error log | `%LOCALAPPDATA%\IsItGreenYet\error.log` | Unexpected exceptions; rotated to `.old` after 512 KiB |
| PAT | Windows Credential Manager, generic credential `IsItGreenYet:github.com` | Only when a PAT is used |

- Before writing, `api.log` and `error.log` mask tokens and the signed download URLs of job logs.
- The paths in `api.log` include repo names. It's a local file; don't commit it to version control or share it.
- Copied failed logs exist only on the clipboard and aren't written to any file.

## Error handling

| Situation | Behavior |
|---|---|
| gh not installed or not signed in; PAT invalid (401) | Main window banner ("Check again", "Open settings") plus a tray badge, guiding you to run `gh auth login` or paste a PAT in Settings (when the token comes from an environment variable, it tells you to restart the app); existing data isn't cleared; no repeated retries. For recovery, see [When signed out](authentication.md#when-signed-out) |
| Insufficient permissions (a 403 that isn't rate limiting) | Only that polling target stops (for example, only the PR list); Repo manager and that repo's rows show the missing permission; other targets and other repos carry on as usual |
| Primary quota used up | Global pause until the quota resets (computed from the response's `Date`, so the local clock doesn't matter); the banner shows the expected reset time. A pause lasts at most 70 minutes (`Tuning.MaxRateLimitWait`): if the computed wait is longer, it's written to error.log, and one more request goes out when the pause ends, pausing again if still rate limited |
| Secondary rate limit | If `retry-after` is present, pause for that long (also 70 minutes at most); otherwise back off starting at 60 seconds and doubling, up to 16 minutes; the banner makes clear that the time shown is when the app plans to retry ("Retrying at …") |
| Unclassifiable 403s from 3 or more repos within 60 seconds | One global 60-second pause; written to error.log |
| Network down | Keeps the last data and shows "Offline · Last updated &lt;time&gt;"; switches to probing with `GET /rate_limit`, and runs a full refresh automatically once back online; no notifications while offline |
| GitHub keeps returning 5xx | Badge plus the banner "GitHub is returning errors"; each target retries under the backoff rules |
| Repo renamed | Follows it to the new name by repo id; URLs are rebuilt with the new name |
| Repo deleted (404) | Refetches the repo list to confirm; removed only after it's missing from two full lists in a row; if it's still in the list, it's flagged and retried once an hour |
| Repo has no workflows | Not shown in the list; Repo manager labels it "No workflows, or Actions is disabled (can't tell which)" |
| Run status is `waiting`/`requested`/`pending`/`action_required` | Separate states (queued, waiting for approval); counted as neither failure nor success |
| Conclusion is `timed_out` or `startup_failure` | Counts as a failure |
| Conclusion is `cancelled`, `skipped`, `neutral`, or `stale` | Not a failure; gray |
| Unrecognized status | Treated as "not completed" (yellow) until it completes; after it completes, an unrecognized conclusion is gray; logged once in error.log |
| PR from a fork (`pull_requests` is empty) | While the PR is open, the number is found by matching against the open PR list (same head SHA and same source repo); if there's no match it's left blank, not guessed (for after the PR is closed, see item 8 in [Known limitations](known-limitations.md)) |
| One commit triggers multiple workflows | One row each |
| A single run returns 404 (past retention, or deleted) | Only that run is marked "no longer exists" and removed from tracking; the local record is kept and the repo isn't affected |
| GitHub 5xx, 422, malformed JSON | Only that target backs off (up to 10 minutes, multiplied further when quota is low); on a JSON error, the response is discarded and the ETag isn't updated; if a single run is missing fields, only that run is skipped; all are written to error.log |
| A list returns 204 or an empty body | Treated as 0 items |
| More than 3 redirects, or HTTPS redirected to HTTP | Treated as an error and not followed; written to error.log |
| API version error (400/410) | Stops all polling, adds the badge, and the banner asks you to update the app |
| Response has `Deprecation`/`Sunset` | Written to error.log; the main window shows a notice once (you can dismiss it with ✕) |
| Job log unavailable (expired, job still running, signed URL expired) | Fetched once more; if it still fails, shows "Couldn't get this job's log (HTTP N)."; doesn't affect the repo's state |
| Clipboard in use | Retries every 100 ms, 3 times in total; shows a message if it still fails |
| A link to open isn't an `https://github.com/` URL | Not opened; written to error.log; the main window also shows a message (links in notifications are only written to error.log; see item 17 in [Known limitations](known-limitations.md)) |
| Credential Manager read/write fails | When saving in Settings: shows the error (including the Windows error code) and keeps the current sign-in method. When reading fails at startup or on "Check again": the main window shows only the generic "Not signed in to GitHub" (see [Deviations from the design specs](spec-deviations.md) (Traditional Chinese)) |
| `%LOCALAPPDATA%` isn't writable | Shows an error at startup that names the path |
| Cache database corrupted (at startup or while running) | Renamed to `cache.db.corrupt-<timestamp>.bak` and kept, and an empty database is rebuilt; at most 5 numbered backups are kept, and after that it's saved as `cache.db.corrupt-latest.bak`, overwriting the previous one (6 backups at most; numbered backups left by an older version count toward the limit and aren't cleaned up, so the total can be higher until you delete them by hand), and the app never deletes or overwrites a numbered backup. A banner says the repos' mute and force-include settings were lost, with "Open repo manager", and it can also be dismissed with ✕; if the file was already gone and this run hasn't kept a backup, the banner says instead that it was rebuilt without keeping a backup and the settings may have been lost. If renaming fails: when the app's initialization finds it at startup, see the next row; when the monitoring engine finds it only while reading or writing (loading data at startup, building the first snapshot, or while running), see item 7 in [Known limitations](known-limitations.md). If the rename and rebuild succeed but the new database reads as corrupted again, only the first backup is kept; also see item 7 in [Known limitations](known-limitations.md) |
| Can't create or open the cache database at startup (an error other than corruption, or corruption found but renaming failed, for example because another program has the file open) | Written to error.log; shows "Couldn't create or open the cache database:" followed by the path and reason, and the app exits after you click "OK" |
| Settings file corrupted | Renamed and kept, defaults restored, and the app starts normally; a banner says so (you can dismiss it with ✕) |
| Settings file can't be read and can't be renamed either (for example, another program has it open and doesn't allow deleting) | This session uses the defaults and leaves the file untouched. Writing is refused (including "Save" in Settings and saving the window position on exit), so your settings aren't overwritten; a banner says so (you can dismiss it with ✕) and it's written to error.log. Restarting after the file is released brings everything back. If the other program allows deleting, or permissions only block reading, the rename succeeds, so even a healthy file takes the row above. If permissions block the rename too (for example, Full control is denied), restarting wouldn't help, so writing isn't refused: this session uses the defaults, it's only written to error.log, and the next save overwrites the file |
| Launched again while already running | Brings back the existing window, and the new process exits (for the exception when it's launched again while the app is shutting down, see item 5 in [Known limitations](known-limitations.md)) |
| Tray unavailable (an exception while creating the icon) | Falls back to a normal window: the window is shown even with `--tray`, and ✕ exits directly; written to error.log. The case where no exception is thrown but the icon doesn't appear can't be detected (see item 1 in [Known limitations](known-limitations.md)) |
| Writing the Start with Windows value fails | Shows an error; this save doesn't take effect at all (other settings aren't saved either), and the "Start with Windows" checkbox goes back to the registry's actual state |
| System clock set back or forward | Scheduling uses a monotonic clock and isn't affected; runs "in the future" show "Just now" |
| Unexpected exception | UI thread: written to error.log, a dialog is shown, and the app keeps running. Background: written to error.log; the same kind of exception is shown with a banner only once per 10 minutes, with no dialog; a failed iteration of the monitoring loop doesn't stop the loop |
| Write: a write is called through some other path while write actions are off | The monitoring engine returns "Writes are turned off, so nothing was sent." and sends no request |
| Write: the token can't write (scope not enough, no write access to the repo, Actions write rejected) | Disabled in advance, or disabled after a rejection (see [Permissions for write actions](authentication.md#permissions-for-write-actions)); the tooltip gives the reason and says you can click "Check connection" in Settings to check again |
| Write: the run had actually finished when you clicked (local state was behind) | GitHub returns 409 or another error, and the error dialog shows GitHub's message; the run is checked once right away and its row is updated to finished |
| Write: someone else re-runs the run while the confirmation dialog is open | "This run has a newer attempt, so nothing was sent. Check its latest status and try again." |
| Write: the repo is muted, skipped, or removed while the confirmation dialog is open | "Couldn't find this repo or run, so nothing was sent." |
| Write: re-running after more than 30 days, the workflow is disabled, or 50 re-runs may have been reached | Disabled in advance with an explanation; when GitHub decides differently, GitHub's response wins. Right after a workflow is disabled, the app may not know yet; see item 30 in [Known limitations](known-limitations.md) |
| Write: offline, paused by rate limiting, signed out, or API version error when sending | The message bar says it wasn't sent; it isn't queued to wait for recovery |
| Write: waited more than 15 seconds for throttling | "Waited too long for a turn to send, so it was dropped. Try again later." |
| Write: timeout, dropped connection, or GitHub returns 5xx | Error dialog "No response from GitHub, so it may already have taken effect. The app will check this run's status automatically." (for 5xx it's "GitHub returned a server error (HTTP N), so it may already have taken effect. The app will check this run's status automatically.", plus GitHub's message, and it's written to error.log); not resent; the run is then checked to confirm its actual state. For a re-run, both kinds of re-run stay disabled until a new attempt appears |
| Write: clicking again right after a re-run | Both kinds of re-run are disabled until GitHub shows a new attempt ("Re-run requested; waiting for GitHub to update"). Right after a re-run, while GitHub still returns the old attempt (queued), the reason for disabling is "Not finished yet"; see item 29 in [Known limitations](known-limitations.md) |
| Write: still not finished more than 5 minutes after cancelling | "Force cancel" appears; "Cancelling" stays until the run finishes |
| Write: the app restarts while a run is "Cancelling" | Neither "Cancelling" nor force cancel is shown anymore, and the row goes back to the state GitHub reports; to force cancel, you first have to send a normal cancel again |
| Write: the app restarts before a re-run is confirmed | Re-runs awaiting confirmation are stored in `cache.db`, and tracking continues after the restart |
| Write: a new attempt never shows up after a re-run | After more than 5 minutes and 3 checks, the special tracking stops, with no message |
| Write: writing while auto-refresh is set to "Paused" | Sent anyway, and tracking after sending works as usual; after a re-run turns into "Notify me", there's no polling and no notification while paused (same as "Notify me") |
| Write: writing after the repo was renamed (3xx) | The redirect isn't followed; the error dialog says the location has changed, and the repo list is fetched again; try again after the list updates to the new name |
| Command line: the app exited normally | Exit code 4, `reason: app_not_running` (`stopped_at` is set) |
| Command line: the app crashed, or the heartbeat is more than 180 seconds old | Exit code 4, `reason: stale` |
| Command line: data not updated for more than 1 hour | Exit code 4, `reason: data_stale` |
| Command line: the app is an older version without the status table, or has never run | Without `--refresh`: exit code 3, `reason: no_status`. With `--refresh`: `refresh_unsupported` when such an older app is running (it has no refresh event); `app_not_running` when the app isn't running (including when it has never run); both are exit code 4 |
| Command line: DB locked for more than 5 seconds, corrupted, or schema version mismatch | Exit code 4, `reason: db_error` or `schema_mismatch`; not renamed or repaired |
| Command line: with `--refresh`, the app isn't running or is in a different logon session | Exit code 4, `reason: app_not_running` |
| Command line: `--refresh` can't open the mutex or event (access denied) | Exit code 4, `reason: refresh_unreachable` |
| Command line: `--refresh` doesn't finish within 210 seconds | Exit code 4, `reason: refresh_timeout`; the current data is still output |
| Command line: with `--refresh`, the app is offline, paused by rate limiting, or signed out | The app reports the refresh as finished right away and sets `refreshPartial: true`, without waiting; the exit code follows the [exit code table](cli.md#exit-codes) (usually 4 `signed_out`, or per `overall`; `data_stale` if the data is more than 1 hour old) |
| Command line: unexpected exception | Exit code 4, `reason: internal_error`; one line of explanation in English is printed to stderr |
| Writing the status table fails (app) | Written to error.log; polling isn't affected; the next write always rewrites the whole row |
| Check for new versions: 404 (no published release yet, or only prereleases) | Silent, with only the request's line in `api.log`: no dialog, banner, or notification, and the tray's "!" badge isn't affected. Counts as completed, so the next check is 3 days later |
| Check for new versions: rate limited, or a network error | Silent in the same way; polling isn't paused and the app doesn't go offline because of it. Doesn't count as completed; retried no sooner than 1 hour later |
| Check for new versions: any other failure (401, another 403, 400, 410, 5xx, malformed JSON, and so on) | Just as silent on screen: it doesn't sign you out or stop polling. One line is also written to error.log; the same kind of failure in a row is written once. Retried no sooner than 1 hour later |
| Check for new versions: an unexpected exception | Just as silent on screen: no banner, and banners from elsewhere and polling aren't affected. Each one is written to error.log with its stack trace. Retried no sooner than 1 hour later. If `cache.db` is really corrupted, the "Cache database corrupted" row applies instead |
| Check for new versions: the tag can't be parsed or is missing, or `html_url` is missing or doesn't start with `https://github.com/` | Counts as completed and as no new version; one line in error.log. The ETag is saved, so an unchanged response comes back as 304 and isn't written again |
| Check for new versions: the running version can't be parsed | No request is sent; written to error.log once per run |
| Check for new versions: the settings file can't be read and stays untouched (the "Settings file can't be read" row above) | Not checked this session, and Settings shows the option unchecked: your choice can't be read, and it may be off |
| Check for new versions: saving the last check time or notified version fails | Only written to error.log, with no message on screen; the values stay in memory and go out with the next successful save |
