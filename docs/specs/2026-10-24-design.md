## 0. 結論先講

1. **做法**：WPF 常駐程式，每個 repo 各自排程，用 `If-None-Match` 輪詢 `GET /repos/{owner}/{repo}/actions/runs`；另以 30 秒一次的 `GET /user/repos?sort=pushed` 第 1 頁探測 push。
   - 依 2026-10-24 實測，你帳號下有 45 個候選 repo，會監看其中 11 個（有 workflow、近 90 天有活動）。
   - 平常每分鐘約 5～6.5 個請求，大多是不扣主額度的 304（§6.7 有可重算的估算）。
   - 帶 token 的 304 不扣主額度：已用你的帳號對 7 個端點實測確認，其中 5 個是輪詢端點（附錄 A）。
2. **API 版本固定送 `X-GitHub-Api-Version: 2026-03-10`**。不送 header 時預設 2022-11-28，這個版本 2028-03-10 停止支援，之後不送 header 的請求會悄悄換版本（§4.1）。
3. **耗時不用 `/timing`**：這個端點已標示停用中（2025-02-02 changelog），改用 `run_started_at` 到 `updated_at`。官方沒有定義這兩個欄位的語意，所以這是推論，驗收時要和網頁比對（§8）。
4. **需要你拍板的事有 10 項**（§21.1）。影響最大的四項：
   - **Q1 並行數**：官方最佳實務要求「序列化請求、不要並行」，和需求的「同時最多 8 個」有出入。建議輪詢 1 條加使用者操作 1 條，合計 2 條，仍在「最多 8」以內。
   - **Q2 Contents read**：需求列的這個權限，沒有任何會用到的端點需要，建議拿掉。
   - **Q3 token**：一把 fine-grained PAT 只能對應一個擁有者；預設的 gh token 則是 `repo` 全權限，包含寫入。
   - **Q4 綠燈的條件**：追蹤的 run 全部是取消或略過時，算不算「全部成功」。
5. **防呆設計**：
   - 3xx 全部自己處理：.NET 自動轉址會清掉 Authorization，私有 repo 改名後會變成未認證請求。token 只送往 `api.github.com`。
   - 收到 401 只重取 token 重試一次，不連續重試：官方說短時間內多次無效憑證，會暫時擋掉該使用者的**所有**驗證，連你自己的 gh 也會被擋。
   - 排程用單調時鐘，不怕系統時間被往回調。
   - 首輪靜默改用「時間界線」判斷，補抓回來的舊失敗不會在啟動時彈出。

## 1. 目標與範圍

### 1.1 目標

一眼看到「我名下所有 repo」的 GitHub Actions 執行狀況，重點是確認 CI 綠燈了沒。

成功標準：

1. 系統匣圖示的顏色加形狀，就能回答「現在有沒有紅的、有沒有在跑的」，不必開視窗。
2. 新 push 觸發的 run，在 run 建立後約 30 秒內出現（探測 30 秒；push 後 15 分鐘內該 repo 每 30 秒輪詢一次，見 §6）。
3. 和 gh CLI、Claude Code、codex 共用每小時 5,000 次的額度。
   - 平常幾乎不扣主額度；就算每個請求都回 200，每小時也只有約 390 次，約 7.8%（§6.7）。
   - 有 run 在跑的 repo，每分鐘多 4 次（15 秒輪詢一次）。

### 1.2 第一階段範圍

唯讀監看：清單、篩選、系統匣狀態、通知、開啟連結、複製失敗 log、repo 管理頁、設定頁。**只看 GitHub Actions workflow runs**。

### 3.1 執行模型與時間來源

**Engine 迴圈**

- Core 的 `MonitorEngine` 跑在一條背景工作上，迴圈本身就是輪詢的序列化佇列。輪詢請求一次只送一個（Q1）。
- Core 不開計時器。App 用一個 1 秒的 `DispatcherTimer` 呼叫 `engine.Tick()`。`Tick()` 只做兩件事：記下這次 tick 的單調時間戳、喚醒迴圈。所以 tick 本身不會重入；迴圈正在等某個請求時，tick 照樣記錄時間戳，供睡眠偵測使用（§6.5）。
- 迴圈每醒來一次，依序做這些事：
  1. 先處理所有排隊的使用者指令（靜音、設定變更、F5），所以這些指令不會排在網路請求後面。
  2. 做睡眠偵測。
  3. 依 §6.3 的節流與優先序挑出一個到期的工作，送出請求。
  4. 處理回應、寫入 DB。
  5. 發布一份不可變的快照（`MonitorSnapshot`）。
  6. 還有到期工作就繼續，沒有就等下一次喚醒。
- App 在 UI 執行緒上依 run id 做差異更新，不整份重建清單，避免清單跳動。
- 使用者操作的請求（複製失敗 log）走另一條工作，和輪詢共用同一個節流器與額度狀態。
- 測試直接呼叫 `RunOnceAsync()`，搭配假的 `HttpMessageHandler` 與 `ManualTimeProvider`。

**時間來源**（三種時間不混用）

| 用途 | 時間來源 | 理由 |
|---|---|---|
| 輪詢到期時間、退避、每分鐘上限的滑動視窗、睡眠偵測、提示停留計時 | 單調時鐘 `TimeProvider.GetTimestamp()`／`GetElapsedTime()` | 系統時間被往回調或 NTP 校時時，排程不會停擺（§15） |
| 和 GitHub 時間戳比較（`lastActivity`、首輪靜默的時間界線、90 天規則、耗時） | 牆鐘 `GetUtcNow()` | GitHub 回傳的是 UTC 時間戳 |
| 顯示 | `GetUtcNow()` 轉 `LocalTimeZone` | 需求：一律用本地時區 |

主額度恢復時間要換算成單調時鐘的期限：`等待秒數 = x-ratelimit-reset − 回應的 Date header`。不用本機牆鐘，本機時鐘快或慢都不影響。

## 4. GitHub API

### 4.1 共通規則

| 項目 | 規則 | 依據 |
|---|---|---|
| Base URL | `https://api.github.com` | — |
| `Accept` | `application/vnd.github+json` | [Getting started › Accept](https://docs.github.com/en/rest/using-the-rest-api/getting-started-with-the-rest-api#accept)（頁首通用建議，不是各端點自己的參數） |
| `User-Agent` | `IsItGreenYet/<版本>` | 沒帶 User-Agent 的請求會被拒（[Getting started › User-Agent](https://docs.github.com/en/rest/using-the-rest-api/getting-started-with-the-rest-api#user-agent)） |
| `X-GitHub-Api-Version` | `2026-03-10` | 見下方說明 |
| `Authorization` | `Bearer <token>`，**只有目標主機是 `api.github.com` 才帶** | 理由見下方「轉址」 |
| `If-None-Match` | 每個輪詢用的 GET 都帶上一次的 ETag，存下什麼就送什麼，不改寫。例外：E9 的 302 與簽名下載網址（一次性請求，Q27） | 見下方說明 |
| 回應容錯 | 見下方說明 | 見下方說明 |
| 同一資料每次用相同 URL | per_page、page、篩選參數固定；完整清單不用會重排的排序 | 參數不同 ETag 就不同；會重排的排序（文件舉 `sort=updated` 為例）會讓已抓過的頁拿不到 304（[Best practices › cacheable requests](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#make-requests-that-can-be-cached)） |
| 分頁 | 只跟 `Link` header 的 `rel="next"`，不自己組 page，不假設一定有 `rel="last"`。每一頁的 ETag 連同「該頁的項目 id 清單」與「next 連結」一起存：304 回應不保證帶 `Link`，回 304 時改用存下的 next | [Using pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api)；304 必帶的 header 不含 `Link`（RFC 9110 §15.4.5） |
| 不解析 API 回傳的 URL | 用 `number`、`id` 等欄位；網頁連結以 API 回傳的 `html_url` 為基底（§10.7） | [Best practices › do not manually parse URLs](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#do-not-manually-parse-urls) |
| 轉址 | 見下方說明 | 見下方說明 |
| 逾時 | 一般請求 30 秒，log 下載 120 秒 | GitHub 處理超過 10 秒會中止請求（[Troubleshooting › timeouts](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#timeouts)），用戶端逾時要比它長 |
| `x-poll-interval` | 回應有這個 header 時，該目標下次間隔取 max(自己的間隔, header 值) | [Best practices › avoid polling](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#avoid-polling) |
| `Deprecation`／`Sunset` header | 寫入 error.log，主畫面顯示一次性提示 | 版本接近停止支援時 GitHub 會帶這兩個 header（[API versions › closing down](https://docs.github.com/en/rest/about-the-rest-api/api-versions#api-version-closing-down)） |
| 400／410（版本錯誤） | 停止所有輪詢、加角標、顯示橫幅請你更新程式 | 指定已停止支援的版本回 410（[API versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions#specifying-an-api-version)）；不存在的版本回 400（[Troubleshooting › not a supported version](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#not-a-supported-version)） |
| 錯誤分類的適用範圍 | §6.4 的錯誤分類與 §13.2 的 401 流程，**只用在 `api.github.com` 的回應**。簽名下載主機的非 2xx 一律只顯示訊息，不改 repo 狀態、不改認證狀態、不觸發全域暫停 | 設計決定；避免 log 下載失敗被誤判成限流 |
| 本機 HTTP 快取 | 不開，每次都真的送出條件請求 | 回應帶 `Cache-Control: private, max-age=60`（實測）。.NET 會不會依它快取沒有查證，實作時從 api.log 的時間與狀態碼觀察 |

**`X-GitHub-Api-Version` 固定送 `2026-03-10`**

- 目前支援 2026-03-10（尚未排定終止）與 2022-11-28（2028-03-10 終止）。
- 不帶 header 時預設 2022-11-28；舊版終止後，不帶 header 的請求會改用「次舊的受支援版本」（[API versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions)）。
- 2026-03-10 的 breaking change 中，和本工具有關的是（[Breaking changes](https://docs.github.com/en/rest/about-the-rest-api/breaking-changes#version-2026-03-10)）：
  - Repository 物件移除 `has_downloads`
  - PR 物件移除 `merge_commit_sha` 與單數 `assignee`
  - `GET /rate_limit` 移除 `rate`（E10 只讀 `resources.core`）

  這些欄位本工具都沒用到。

**`If-None-Match` 的實測**：官方說 304 而且帶正確 Authorization 時不扣主額度（[Best practices › conditional requests](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#use-conditional-requests)），但 actions 端點頁只列 200、沒列 304。所以另外實測：帶 token 對 7 個端點連續送條件請求，全部回 304，`x-ratelimit-used` 不變（附錄 A）。304 算不算次級限制，文件沒寫。

**回應容錯**

- 時間戳一律當 UTC ISO 8601 解析；欄位可能是 null；不認得的欄位忽略（[Getting started › response body](https://docs.github.com/en/rest/using-the-rest-api/getting-started-with-the-rest-api#about-the-response-body)）。
- 不認得的 status／conclusion 字串不丟例外（§7.1）。新增欄位、新增 enum 值屬於非破壞性變更，會出現在所有受支援的版本（[API versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions#about-api-versioning)）。
- 列表回 204 或空 body 時，當作 0 筆。部分端點沒資料時回 204（[Pagination 範例註解](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api#example-creating-a-pagination-method)）。

**轉址**

- `AllowAutoRedirect = false`，自己處理 301／302／307／308，最多 3 次。
  - .NET 自動轉址時，不論是否同主機，都會清掉 Authorization（[SocketsHttpHandler.AllowAutoRedirect](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.socketshttphandler.allowautoredirect?view=net-10.0)；dotnet/runtime `RedirectHandler.cs` 第 52–53 行，查證代理也在本機實測過）。
  - 所以私有 repo 的轉址請求會變成未認證。
- 目標是 `api.github.com` 才重新帶 Authorization；其他主機（例如 job log 的簽名網址）不帶。
- GitHub 要求跟隨轉址：301 是永久轉址，之後改用新 URL；302／307 不要（[Best practices › follow redirects](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#follow-redirects)）。
- 本工具的 301 做法：
  - 照 `Location` 重送這一次，但**不把 `Location` 存成之後的輪詢網址**。`Location` 可能是官方沒有文件的 `/repositories/{id}/…` 形式。
  - 排入一次 repo 完整重抓，用 repo id 對照出新的 `full_name`，再重組 `/repos/{owner}/{repo}/…` 網址（§5.4）。
- 「repo 改名後 REST 子路徑會回 301」是推論：官方只說網頁與 git 操作會轉址，唯一明講 REST 的是 2015 年的舊文。所以 §5.4 對 404 也有改名偵測。

### 4.2 第一階段使用的端點

每個端點的參數、欄位、權限都以官方文件為準，並和官方 OpenAPI 描述（github/rest-api-description）交叉核對。標「實測存在」的欄位，已在 2026-10-24 用你的帳號確認回應中確實有這個欄位（只看欄位名稱，沒有記錄內容）。

| # | 端點 | 用途 | 實際使用的參數 | fine-grained 權限 |
|---|---|---|---|---|
| E1 | `GET /user` | 取得我的 `login`、`id` | — | 不需要 |
| E2 | `GET /user/repos` | repo 清單與 push 探測 | `affiliation`、`per_page=100`（探測另加 `sort=pushed`） | Metadata: read |
| E3 | `GET /repos/{owner}/{repo}/actions/workflows` | 有沒有 workflow、workflow 狀態 | `per_page=100` | Actions: read |
| E4 | `GET /repos/{owner}/{repo}/actions/runs` | 主要輪詢；PR 分支補抓 | `per_page=30`；補抓時另加 `head_sha` | Actions: read |
| E5 | `GET /repos/{owner}/{repo}/actions/workflows/{workflow_id}/runs` | 補抓某 workflow 在預設分支的 run | `branch={default_branch}`、`per_page=5` | Actions: read |
| E6 | `GET /repos/{owner}/{repo}/actions/runs/{run_id}` | 單筆 run 更新 | — | Actions: read |
| E7 | `GET /repos/{owner}/{repo}/pulls` | 開啟中的 PR | `state=open`、`per_page=100` | Pull requests: read |
| E8 | `GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs` | 複製失敗 log：找失敗的 job | `filter=latest`、`per_page=100` | Actions: read |
| E9 | `GET /repos/{owner}/{repo}/actions/jobs/{job_id}/logs` | 複製失敗 log：下載 job log | — | Actions: read |
| E10 | `GET /rate_limit` | 啟動時取得額度、離線時探測連線 | — | 不需要 |
| E15 | `GET /repos/{owner}/{repo}/releases/latest` | 檢查新版本（§9.6）；`{owner}/{repo}` 是本專案自己的 repo，不是監看中的 repo | 有上次檢查時間才帶 `If-None-Match` | Contents: read（官方權限頁）；沒有這個權限時讀公開 repo 能不能成功，不確定（手動測試清單 M65 實測） |

#### E1 `GET /user`

- 文件：[Get the authenticated user](https://docs.github.com/en/rest/users/users#get-the-authenticated-user)
- 這個端點沒有任何路徑或查詢參數。
- 使用欄位：`login`、`id`、`type`。三者在 public 與 private user 回應中都是 required，實測存在。
- 狀態碼（文件）：200、304、401、403。
- 時機：啟動時、認證方式或 token 改變時、「重新檢查」時。
- 比對「是不是我」一律用 `id`（login 可以改名），顯示用 `login`。

#### E2 `GET /user/repos`

- 文件：[List repositories for the authenticated user](https://docs.github.com/en/rest/repos/repos#list-repositories-for-the-authenticated-user)
- 參數（文件確認存在）：
  - `affiliation`：逗號分隔，可選 `owner`、`collaborator`、`organization_member`；預設三者都含。
  - `sort`：`created`、`updated`、`pushed`、`full_name`，預設 `full_name`。`direction` 在 `full_name` 時預設 `asc`，其他（含 `pushed`）預設 `desc`。
  - `per_page`：預設 30、上限 100。超過上限不報錯，會被悄悄降到 100。
  - **不送 `type`**：`type` 和 `visibility` 或 `affiliation` 同時出現會回 422。
- 本工具送的 URL（每種都固定不變，ETag 才有效）：
  - 清單 A（完整清單，跟著 `Link` 分頁）：`/user/repos?affiliation=owner,organization_member&per_page=100`
  - 清單 B（完整清單）：`/user/repos?affiliation=collaborator&per_page=100`
  - 探測 A：`/user/repos?affiliation=owner,organization_member&sort=pushed&per_page=100`，只抓第 1 頁
  - 探測 B：`/user/repos?affiliation=collaborator&sort=pushed&per_page=100`，只抓第 1 頁
- 完整清單用預設排序，因為 `sort=pushed` 依同理也會重排（推論）。探測本來就是要在 push 時看到變化，所以用 `sort=pushed`。
- 使用欄位（文件確認，實測存在）：`id`（int64）、`name`、`full_name`、`owner.login`、`owner.id`、`owner.type`、`private`、`visibility`、`fork`、`archived`、`disabled`、`pushed_at`（**可為 null**）、`default_branch`、`html_url`。
- 狀態碼（文件）：200、304、401、403、422（422 也可能代表「endpoint has been spammed」）。
- 注意：
  - `affiliation=organization_member` 涵蓋「透過組織成員身分可存取的 repo」，文件明寫包含所在每個 team 的每個 repo。只靠組織 base permission、不在任何 team 的 repo 會不會列出，文件沒寫。你目前不屬於任何組織（`GET /user/orgs` 實測 0 個），暫時不影響。
  - 文件對 `affiliation=owner` 的定義只有「本人擁有的 repo」，「不含組織擁有的 repo」是推論。本工具不靠 affiliation 區分自己與組織的 repo，而是比對 `owner.id`（§5.1），所以不受影響。
  - 用 fine-grained PAT 時，是否只回傳該 token 選定的 repo，文件沒寫，實作後實測。

#### E3 `GET /repos/{owner}/{repo}/actions/workflows`

- 文件：[List repository workflows](https://docs.github.com/en/rest/actions/workflows#list-repository-workflows)
- 參數：`per_page`（上限 100）、`page`。
- 使用欄位（實測存在）：`total_count`、`workflows[].id`、`name`、`path`、`state`、`html_url`。
- `state` 的允許值：`active`、`deleted`、`disabled_fork`、`disabled_inactivity`、`disabled_manually`。2026-10-24 實測，你有 3 個 repo 帶有 `disabled_manually` 的 workflow。
- 狀態碼（文件）：只列 200。

#### E4 `GET /repos/{owner}/{repo}/actions/runs`

- 文件：[List workflow runs for a repository](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-repository)
- 參數（文件確認存在）：`actor`、`branch`、`event`、`status`、`per_page`（預設 30、上限 100）、`page`、`created`、`exclude_pull_requests`（預設 false）、`check_suite_id`、`head_sha`。
  - `status` 允許 14 個值：`completed`、`action_required`、`cancelled`、`failure`、`neutral`、`skipped`、`stale`、`success`、`timed_out`、`in_progress`、`queued`、`requested`、`waiting`、`pending`（**不含 `startup_failure`**）。
- 本工具的兩種用法：
  - **主要輪詢**：只送 `per_page=30`，不帶任何篩選。
    - 帶 `actor`、`branch`、`created`、`event`、`status` 等篩選時，每次搜尋最多只回 1,000 筆。
    - `created` 只依建立時間篩選，會漏掉之前就開始、仍在跑或被重跑的 run。
    - 30 是官方預設值，回應比 100 筆小得多，也比較不會碰到 10 秒逾時。
  - **PR 分支補抓**：`?head_sha={PR 的 head.sha}&per_page=30`，帶 ETag；每個 head sha 只抓一次（§7.2）。
- 使用欄位（文件確認，實測存在）：
  - `total_count`
  - `workflow_runs[].id`（int64）
  - `name`（可為 null）
  - `display_title`
  - `run_number`
  - `run_attempt`（schema 非 required，缺值當 1）
  - `event`
  - `status`、`conclusion`（都可為 null）
  - `workflow_id`
  - `head_branch`（可為 null）
  - `head_sha`
  - `path`
  - `actor.login`、`actor.id`（`actor` schema 非 required；缺值時 N2 不觸發、顯示留白）
  - `triggering_actor.login`（非 required）
  - `run_started_at`、`created_at`、`updated_at`
  - `html_url`
  - `pull_requests[]`：`number`、`head.ref`、`head.sha`、`head.repo.id`、`base.ref`
  - `head_repository.id`、`head_repository.full_name`、`head_repository.html_url`：`head_repository` 是 required 的 Minimal Repository，`id` 是它的 required 欄位。不用頂層、非 required 的 `head_repository_id`。
  - `previous_attempt_url`
- 官方說明：
  - `run_started_at` 是最新一次 attempt 的開始時間，重跑時會重設。
  - `run_attempt` 從 1 開始，重跑時遞增。
  - `display_title` 是事件專屬的標題；workflow 有設 `run-name` 時就是 run-name。
  - `pull_requests` 只包含 head_sha 或 head_branch 相符、**而且仍開啟中**的 PR，不一定是觸發這次 run 的 PR。
- 文件沒有寫，本工具的對應做法：
  - **回傳順序**：一律自己用 `run_number`／`created_at` 排序，不取「陣列第一筆」。「第 1 頁包含最新的 30 筆」是推論，驗收時拿網頁順序比對。
  - `created_at`／`updated_at` 的語意：沒寫。
  - run 物件 `status`／`conclusion` 的完整值清單：schema 沒有 enum，可能新增值。
  - **fork PR 的 run**：workflow runs 文件沒寫。check suites 文件說推到 fork 分支的 push 會回空的 `pull_requests`、`head_branch` 為 null（[Get a check suite](https://docs.github.com/en/rest/checks/suites#get-a-check-suite)），套用到 workflow run 屬於推論，所以 `head_branch` 一律當成可為 null。
- 狀態碼（文件）：只列 200，沒有列 304；但實測帶 ETag 時確實回 304，而且不扣主額度（附錄 A）。
- 另一份不帶 token、只有一個樣本的實測（事實表 gap-1）顯示：run 進行中、job 往前推進時，單筆 run 端點仍回 304，直到 run 轉成 completed 才回 200；jobs 端點則幾乎每輪都變。所以：
  - 進行中的 run 只輪詢 runs 端點，jobs 只在複製 log 時抓。
  - 「runs 列表在 job 推進期間也維持 304」是推論，用驗收第 4 項的 304 比例確認。
- 資料保留：2026-10-01 起保留期也套用到 workflow runs，預設 90 天，過期永久刪除（[changelog 2026-10-01](https://github.blog/changelog/2026-10-01-actions-retention-now-covers-checks-runs-and-statuses/)）；私有 repo 可設 1～400 天。

#### E5 `GET /repos/{owner}/{repo}/actions/workflows/{workflow_id}/runs`

- 文件：[List workflow runs for a workflow](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-workflow)
- 參數與 E4 相同，多了路徑參數 `workflow_id`：可以填整數 ID，也可以填 workflow 檔名。本工具用整數 ID 轉成字串。同樣有 1,000 筆上限，本工具只取 5 筆，不受影響。
- 觸發條件：某個 active workflow 的預設分支鍵（§7.2），符合下列任一情況：
  - 本地沒有任何 run
  - 本地找不到 `lastDecisive`（只有未完成、灰色或未知的 run）
- 做法：送 `branch={default_branch}&per_page=5`，在回傳中只留 `head_repository.id == repo.id` 且 event 屬於規則 1 的 run，依 `run_number` 取最大的當 latest，再往下找 lastDecisive。
- 5 筆內都找不到決定性結論時，該鍵標成「未知」（§7.3）；`SeedRecheck`（1 小時）後再查（ETag）。
- 這個端點的 304 行為沒有實測，列入驗收第 4 項。

#### E6 `GET /repos/{owner}/{repo}/actions/runs/{run_id}`

- 文件：[Get a workflow run](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run)
- 兩種用途：
  - 追蹤中、或被標記「完成時通知我」的 run 還沒完成，卻不在最近一次 E4 第 1 頁裡（例如舊 run 被重跑）：用所屬 repo 的間隔輪詢。
  - 本地顯示未完成、但不在最近一次 E4 第 1 頁、也不是上一種的 run：用 `QuietMax`（5 分鐘）輪詢，直到完成或回 404。避免它永遠停在「進行中」。
- 狀態碼（文件）：只列 200。
- 回 404（例如過了保留期、被人刪掉）時：只把這筆 run 標成「已不存在」並移出追蹤，保留本地紀錄，**不觸發** §5.4 的 repo 流程。

#### E7 `GET /repos/{owner}/{repo}/pulls`

- 文件：[List pull requests](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests)
- 參數（文件確認）：`state`（`open`／`closed`／`all`，預設 `open`）、`head`、`base`、`sort`（預設 `created`）、`direction`、`per_page`、`page`。
- 本工具送 `state=open&per_page=100`，用預設排序，穩定。
- 使用欄位：
  - `number`、`html_url`
  - `head.ref`、`head.sha`
  - `head.repo.id`、`head.repo.full_name`（文件標 required，保守起見仍當成可為 null）
  - `user.login`（可為 null）
- 狀態碼（文件）：200、304、422。
- 只需要「開啟中」的 PR：PR 不在開啟清單裡，就代表已合併或已關閉，不用逐一查 `GET /pulls/{n}`。
- 分支被改名時，以它為 head 的開啟中 PR 會被 GitHub 關閉（[Renaming a branch](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-branches-in-your-repository/renaming-a-branch)），同樣會從清單消失。
- 回 403／404 時：只停這個 repo 的 PR 追蹤，標示「缺少 Pull requests 權限或無法存取」，該 repo 的 PR 鍵狀態變成「未知」，E4 照常輪詢。

#### E8 `GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs`

- 文件：[List jobs for a workflow run](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run)
- 參數：`filter`（`latest`／`all`，預設 `latest`，只回最近一次 attempt）、`per_page`（上限 100）、`page`。
- 使用欄位（實測存在）：`total_count`、`jobs[].id`、`name`、`status`、`conclusion`（可為 null）、`started_at`、`completed_at`（可為 null）、`html_url`。
- job 的 `conclusion` 值域是 success、failure、neutral、cancelled、skipped、timed_out、action_required，沒有 `stale` 與 `startup_failure`。
- 超過 100 個 job（matrix）時，依 `Link` 分頁。

#### E9 `GET /repos/{owner}/{repo}/actions/jobs/{job_id}/logs`

- 文件：[Download job logs for a workflow run](https://docs.github.com/en/rest/actions/workflow-jobs#download-job-logs-for-a-workflow-run)
- 回應：302，`Location` 指向純文字 log，**轉址網址 1 分鐘後失效**。
- 處理：
  - 拿到 `Location` 立刻下載，不帶 Authorization、不快取。
  - log 只記主機與路徑，查詢字串換成 `?***`（裡面有簽名）。
  - 下載主機回非 2xx 時，重新呼叫 E9 一次；仍失敗就顯示「拿不到這個 job 的 log（狀態碼 N）」。
  - 這些錯誤不改 repo 狀態，也不觸發全域暫停（§4.1）。
- log 過期、或 job 還在跑時會回什麼，文件沒寫。
- 這是使用者按了才送的一次性請求，回應是一次性的簽名網址，所以不帶 `If-None-Match`（Q27）。

#### E10 `GET /rate_limit`

- 文件：[Get rate limit status for the authenticated user](https://docs.github.com/en/rest/rate-limit/rate-limit#get-rate-limit-status-for-the-authenticated-user)
- 不扣主額度，但可能計入次級限制；只讀 `resources.core`。
- 時機：啟動時一次；離線時用來探測連線恢復（§6.4），有退避。
- 平常的額度狀態一律以每個回應的 `x-ratelimit-*` header 為準，兩者不一致時以 header 為準。

#### E15 `GET /repos/{owner}/{repo}/releases/latest`

- 文件：[Get the latest release](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)
- 編號接在[第二階段設計規格](2026-10-29-phase2-design.md)的 E14 之後。`{owner}/{repo}` 是本專案自己的 repo（`Tuning.ProjectRepoFullName`）。
- 官方定義的 latest release：不是 prerelease、不是 draft，依 `created_at` 最新的那一筆。所以 prerelease 與 draft 不會從這裡回來。
- 使用欄位：`tag_name`、`html_url`。缺欄位不算 JSON 錯誤，處理見 §9.6。
- 狀態碼（文件，2026-11-04 查）：200、404，沒有列 304。條件請求實際回不回 304 列入手動測試清單 M65；不回 304 也不影響邏輯，只是這個請求會扣主額度。
- fine-grained 權限（2026-11-04 查）：[權限頁](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)把這個端點列在 Contents: read，同一頁也說有些端點讀公開資源不需要這些權限，但沒有針對這個端點講，端點頁也沒有寫。本專案不申請 Contents（§4.4），所以沒有這個權限的 PAT 讀不讀得到公開 repo 的 release，不確定，列入 M65；讀不到時再改 §4.4 與 `docs/authentication*.md`。
- 時機：§9.6。

### 4.3 刻意不用的端點

| 端點 | 不用的原因 |
|---|---|
| `GET .../actions/runs/{run_id}/timing`（Get workflow run usage） | 端點頁標示停用中；[2025-02-02 changelog](https://github.blog/changelog/2025-02-02-actions-get-workflow-usage-and-get-workflow-run-usage-endpoints-closing-down/) 宣布關閉，沒有給端點的移除日期 |
| `GET .../branches/{branch}` | 要 Contents read（同一權限會一併開放讀程式碼）。追蹤範圍只有預設分支與開啟中 PR 的分支，用 E7 就夠 |
| `GET .../pulls/{pull_number}` | 只需要知道 PR 是否仍開啟，E7 一次就能取得整個 repo 的開啟中 PR |
| `GET /user/orgs` | E2 的 `organization_member` 已涵蓋組織 repo；而且用 fine-grained token 呼叫一律回 200 空清單，不能拿來判斷 |
| `GET .../commits/{ref}/status` | GitHub Actions 產生的是 checks，不是 commit statuses；只用 Actions 的 repo，這裡會永遠是 pending |
| `GET .../actions/permissions` | 唯一分得出「沒有 workflow」與「Actions 已停用」的官方端點，但需要 Administration read，超出第一階段權限 |
| `GET /repositories/{id}` | 官方沒有文件。repo 改名改用「重抓 repo 清單、以 id 對照」處理 |

### 4.4 權限需求

| 權限 | 需要的端點 | 第一階段 |
|---|---|---|
| Actions: read | E3、E4、E5、E6、E8、E9 | 需要 |
| Metadata: read | E2 | 需要 |
| Pull requests: read | E7 | 需要 |
| Contents: read | 監看與操作都沒有端點需要（只有 `GET .../branches/{branch}` 一定要它，但不用這個端點）。E15 在官方權限頁列在這裡，但只讀公開 repo，沒有這個權限時能不能成功要實測（手動測試清單 M65） | **不申請（Q2）** |
| Actions: write | 第二階段的重跑、取消 | 第一階段不申請 |

各端點權限出處：[Permissions required for fine-grained personal access tokens](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)，以及各端點頁的「Fine-grained access tokens」段落。

和 token 類型有關、會影響設計的限制：

- **fine-grained PAT 只能選一個 resource owner**（一個使用者或一個組織），也不能同時存取多個組織（[Managing your personal access tokens › limitations](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#fine-grained-personal-access-tokens-limitations)）。
- 官方列出的缺口包括：fine-grained PAT 不能用來**對**自己只是 outside collaborator 或 repository collaborator 的 repo **做貢獻**。
- 讀取方面：
  - 公開 repo：fine-grained PAT 一律可讀。
  - 組織 repo 的 outside collaborator：只能用 classic PAT 存取。
  - 其他個人帳號擁有、你只是 collaborator 的私有 repo：因為 resource owner 只能選自己，推論讀不到，列入實測。
- 組織預設要求核准 fine-grained PAT，核准前只能讀公開資源；組織預設的最長效期政策是 366 天。
- gh CLI 是 GitHub 的 privileged OAuth app，組織的 OAuth app access restrictions 擋不住它（[Privileged OAuth apps](https://docs.github.com/en/apps/oauth-apps/using-oauth-apps/privileged-oauth-apps)）。
- 經由 gh 瀏覽器／裝置登入取得的 token，最小 scope 一定含 `repo`（[gh auth refresh](https://cli.github.com/manual/gh_auth_refresh)），而 `repo` 是公開與私有 repo 的完整讀寫權限。
  - 換句話說，用 gh token 時「唯讀」只能靠程式自律，權限上沒有保證（Q3）。
- gh 給的 token 不一定是上面那種：
  - `GH_TOKEN`／`GITHUB_TOKEN` 環境變數會蓋過 gh 自己存的憑證。
  - 用 `gh auth login --with-token` 存入的 fine-grained PAT，gh 也不會檢查 scope。
  - 所以程式執行時讀回應的 `X-OAuth-Scopes`：有值但不含 `repo` 時，在設定頁提示「這個 token 可能看不到私有 repo」；header 不存在或值為空時不判斷（fine-grained PAT 屬於哪一種，官方沒寫）。
- classic PAT 遇到要求 SAML SSO 但未授權的組織時（[Authenticating › SAML SSO](https://docs.github.com/en/rest/authentication/authenticating-to-the-rest-api#personal-access-tokens-and-saml-sso)）：
  - 存取單一組織的資源：回 404 或 403。
  - 跨組織的列表：直接少掉該組織的資源，並帶 `X-GitHub-SSO: partial-results`。
  - gh 的 OAuth token 是否同樣如此，是推論。收到 `X-GitHub-SSO` 時顯示一次性提示。
- Checks API：check-runs 端點頁寫 fine-grained PAT 可用；但 PAT 的限制清單、fine-grained 權限總表、「Endpoints available for fine-grained PATs」頁、2025-03-18 GA changelog 都沒有它或明寫不行。第三階段要另外實測。

## 5. 監看範圍與 repo 探索

### 5.1 repo 分類

| 類別 | 判定 | 預設 |
|---|---|---|
| 自己的 | 出現在清單 A，且 `owner.id == 我的 id` | 監看 |
| 組織的 | 出現在清單 A，且 `owner.id != 我的 id` | 監看 |
| 協作 | 只出現在清單 B | 略過（設定「包含協作 repo」開啟後監看） |
| fork | `fork == true`（不論出現在哪個清單） | 略過（設定「包含 fork」開啟後監看） |

- 同時出現在 A 與 B 的 repo，以 A 為準。
- 清單 B 與探測 B 的抓取時機：
  - 設定「包含協作 repo」開啟時
  - 有任何被強制納入的協作 repo 時
  - 開啟 repo 管理頁時抓一次（需要列出「所有看得到的 repo」）
- **候選 repo**：通過 §5.2 第 1～5 條（沒有被靜音、封存、停用，也沒有因 fork 或協作身分被排除）的 repo。

### 5.2 自動略過與手動覆寫

依序判斷，命中第一個就停：

| 順序 | 條件 | 狀態與原因文字 | 可強制納入 |
|---|---|---|---|
| 1 | 手動靜音 | 略過：已靜音 | —（取消靜音即可） |
| 2 | `archived` | 略過：已封存 | 否（封存後 repo 唯讀、不能 push，推論不會再有新 run；官方沒有明寫。Q30） |
| 3 | `disabled` | 略過：已停用 | 否（Q30） |
| 4 | fork 且設定未開啟 | 略過：fork | 是 |
| 5 | 協作且設定未開啟 | 略過：協作 repo | 是 |
| 6 | `pushed_at` 超過 90 天（或為 null）**且**本地沒有 90 天內的 run 紀錄 | 略過：超過 90 天沒有活動 | 是（只有排程 workflow 的 repo 用這個救回來） |
| 7 | workflow 總數為 0 | 略過：沒有 workflow | 否（Q30） |
| 8 | workflow 全部不是 `active` | 略過：workflow 都已停用 | 否（Q30） |
| 9 | 某個端點回非限流的 403／404 | 監看中，但標示問題（§5.4、§6.4） | — |
| — | 其他 | 監看中 | — |

- 第 6 條：
  - 需求原文是「本地沒有任何 run 紀錄」。
  - 第一次啟動時每個 repo 的本地紀錄都是空的，照原文會把只靠排程執行的 repo 全部略過，所以加了「首次檢查」（Q7）。
  - 「90 天內」是配合 GitHub 預設保留期加的條件。
- 第 7 條：Actions 被停用時 API 會回 0 筆、403 還是 404，文件都沒寫。只有需要 Administration read 的 `actions/permissions` 分得出來，第一階段做不到。所以 Actions 停用可能落在第 7 條、第 9 條或 §5.4，原因文字寫「沒有 workflow（或 Actions 已停用，無法分辨）」。
- 靜音與強制納入存在 `cache.db` 的 `repo_overrides`，以 repo `id` 為鍵（改名不影響），不寫進設定檔。
- 被略過的 repo 不輪詢 runs，也不出現在主清單；只在 repo 管理頁列出。
- **重新分類的時機**：
  - 探測發現 `pushed_at` 變動時
  - 每次完整重抓後
  - 每次 workflow 清單更新後
  - 使用者變更靜音、強制納入或設定時

  都對該 repo 重跑一次上表。從略過轉成監看時，立即排入 E3 與 E4，並設定首輪的時間界線（§9.3）。

### 5.3 repo 清單的維護

| 動作 | 時機 | 請求 |
|---|---|---|
| 完整重抓 | 每小時；啟動時一次（帶 ETag；暫停模式沒有這一輪，§6.6）；開啟 repo 管理頁時（§5.1）；設定「包含協作／fork」改變時；收到 repo 請求的 301 或 404 時；暫停模式下這次執行還沒抓完過清單時的全量刷新（§6.6） | 清單 A 全部分頁（＋清單 B，依 §5.1） |
| push 探測 | 每 30 秒（§6.2） | 探測 A 第 1 頁（＋探測 B 第 1 頁，依 §5.1） |
| workflow 清單 | 每個未被第 6 條略過的候選 repo 每小時一次（含被第 7、8 條略過的，這樣網頁上重新啟用 workflow 最多 1 小時就會發現）；該 repo `pushed_at` 改變時立即；E4 出現本地沒有的 `workflow_id` 時立即 | E3 |
| stale repo 的首次檢查（Q7） | 第一次看到被第 6 條略過的 repo 時，只做一次 | E3；有 workflow 才 E4（同主要輪詢的 URL） |

探測依 `sort=pushed` 由新到舊排序，最近 push 的 repo 一定在第 1 頁。每次拿到 200，就逐一比對 `pushed_at`：

- 有變動：重新分類；監看中的 repo 立即排 E4，並排入 E3 與 E7。
- 出現新的 repo id：立即分類。

repo 物件的任何欄位（例如 open issue 數）變了，第 1 頁的 ETag 就會變，所以探測不是每次都 304，但這樣的 200 也只扣 1 次。

排程、手動觸發、重跑都不會改變 `pushed_at`（這些事件不產生新的 push），這些 run 靠各 repo 自己的輪詢抓到，安靜的 repo 最多延遲 5 分鐘。

### 5.4 改名、刪除、失去存取

這一節只適用於 E4 與 E3 的回應。E5、E6、E7 的錯誤只影響那個目標（§4.2）。

| 情況 | 行為 |
|---|---|
| E4／E3 回 301 | 照 `Location` 重送這一次（`api.github.com` 才帶 token），不保存 `Location`；排入一次完整重抓 |
| E4／E3 回 404 | 不立刻刪除，排入一次完整重抓 |
| 完整重抓後，同一個 id 的 `full_name` 變了 | 當成改名：更新 `full_name` 與 `html_url`，所有網址用 `/repos/{owner}/{repo}` 重組，刪掉舊網址的快取，立即重送 |
| 完整重抓後，id 不見了 | 只有在「該輪所有分頁都成功」時才算數；**連續兩輪**都不見，才移出監看、從主清單移除並刪除本地 run 紀錄。分頁中途失敗、或只有一輪不見，都不算 |
| 完整重抓後，id 還在、名稱沒變，E4 卻回 404 | 標示「Actions 端點回 404：可能是 token 對這個 repo 沒有 Actions 權限（fine-grained PAT 沒選這個 repo、待組織核准、效期不符、SSO 未授權）」，改成每小時重試一次 |

依據：

- GitHub 對部分私有資源在沒有權限時回 404，而不是 403，以免透露私有 repo 是否存在（[Troubleshooting › 404](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#404-not-found-for-an-existing-resource)）。所以 404 不能直接判定為「已刪除」。
- 官方也要求反覆收到 404 時，先排除授權問題，再大幅拉長間隔（[Best practices › do not ignore errors](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#do-not-ignore-errors)）。
- fine-grained PAT 一律附帶所有公開 repo 的唯讀權限，所以權限不足時 `/user/repos` 可能照樣回 200，只是少了私有 repo，不會報錯。設定頁的「檢查連線」會顯示「看得到 N 個 repo（其中私有 M 個）」，讓你發現這種情況。

需求寫「repo 被刪除（404）→ 移出清單」，這裡改成「確認後才移出」，列在 Q29。

## 6. 輪詢與 API 額度

### 6.1 輪詢目標

**所有週期性目標的間隔都乘上低額度倍率 `k`（§6.4）**，也都受鎖定下限 `LockedMinInterval` 約束。

| 目標 | 請求 | 基本間隔（再乘 `k`） |
|---|---|---|
| push 探測 | E2 第 1 頁 | `ProbeInterval` |
| repo runs（每個監看中的 repo 一個） | E4 | §6.2 公式 |
| 單筆 run：追蹤中或被標記，還沒完成又不在第 1 頁 | E6 | 同所屬 repo |
| 單筆 run：本地顯示未完成，不在第 1 頁 | E6 | `QuietMax` |
| 開啟中 PR（每個監看中的 repo 一個） | E7 | 該 repo 有 PR 鍵處於 `failing` 或 `keyPending` 時用 `PullListTtlActive`，否則 `PullListTtl`（Q25）。另外在「出現新的 `pull_request*` 事件 run」或「該 repo `pushed_at` 改變」時立即抓 |
| PR 分支補抓 | E4 加 `head_sha` | 每個 head sha 一次 |
| 預設分支補抓 | E5 | 觸發時一次；查不到時 `SeedRecheck` |
| workflow 清單 | E3 | `WorkflowsRefresh`（§5.3） |
| repo 完整清單 | E2 全部分頁 | `RepoListRefresh`；這次執行還沒抓完過時，失敗後的重試用 `QuietMax`（第一次載入不必為一次 5xx 等一小時，§6.6） |
| 錯誤狀態的目標 | 同上 | `PermissionRetryInterval`／`NotFoundRetryInterval` |

### 6.2 間隔公式

符號：

- `lastActivity`：這個 repo 已知所有 run 的 `max(created_at, updated_at)`，與 repo 的 `pushed_at`，三者取最大；都沒有時，視為「很久以前」。需求原文是「距最後一次 run 的時間」，加入 `pushed_at` 的理由見下方（Q28）。
- `repoRunning`：以下兩種 run 中，有任何一筆的判定類別是「未完成」（§7.1：queued、in_progress、requested、pending，或不認得的非 completed 狀態）：
  - 這個 repo 最近一次 E4 第 1 頁回應裡的 run
  - 追蹤中或被標記的 run

  不看本地殘留的其他舊 run。
- `k`：低額度拉長倍率（§6.4）。
- `locked`：螢幕鎖定中。

```
base     = repoRunning ? ActiveRepoInterval
                       : clamp((now − lastActivity) ÷ QuietDivisor, QuietMin, QuietMax)
interval = base × k
if locked:  interval = max(interval, LockedMinInterval)
```

| 常數 | 值 | 依據 |
|---|---|---|
| `ActiveRepoInterval` | 15 秒 | 需求 |
| `QuietDivisor` | 30 | 需求 |
| `QuietMin` | 30 秒 | 需求 |
| `QuietMax` | 300 秒 | 需求 |
| `LockedMinInterval` | 300 秒 | 需求 |
| `ProbeInterval` | 30 秒 | 需求「30–60 秒」取下限 |

說明：

- `repoRunning` 和 §7.2 的 `keyPending` 是兩個不同的東西，名稱刻意分開：
  - `repoRunning` 只看「未完成」類別，決定要不要 15 秒輪詢。
  - `keyPending` 還包含「等待」類別，決定系統匣顏色。
- `waiting` 與 `action_required` 依需求視為「等待」狀態，不算 `repoRunning`，用安靜公式。這類狀態可能持續數天，15 秒輪詢沒有意義。注意：官方對 `action_required` 的定義和「等待核准」不是同一件事（§7.1）。
- 把 `pushed_at` 算進 `lastActivity` 的理由：push 之後 GitHub 要幾秒才會建立 run，立即抓的那一次常常還看不到。算進去之後，push 後 15 分鐘內（900 ÷ 30 = 30 秒）該 repo 每 30 秒輪詢一次，run 一出現就轉成 15 秒。
- 「自動更新」選了固定秒數時，`base` 換成該秒數（探測也是），其餘規則（ETag、`k`、鎖定下限）照舊。
- 選「暫停」時不排任何週期性輪詢；F5 與系統匣「立即刷新」仍可手動觸發一次全量刷新。

可重算的例子（`k = 1`，未鎖定）：

| 距 lastActivity | 計算 | 間隔 |
|---|---|---|
| 5 分鐘 | 300 ÷ 30 = 10 → 下限 30 | 30 秒 |
| 15 分鐘 | 900 ÷ 30 = 30 | 30 秒 |
| 1 小時 | 3600 ÷ 30 = 120 | 120 秒 |
| 2.5 小時 | 9000 ÷ 30 = 300 | 300 秒 |
| 1 天 | 86400 ÷ 30 = 2880 → 上限 300 | 300 秒 |

### 6.3 自我節流

| 規則 | 值 | 依據 |
|---|---|---|
| 輪詢請求同時數 | 1（Engine 迴圈本身就是佇列） | 官方最佳實務：為了避開次級限制，請求要序列化、不要並行，可以用佇列實作（[Best practices › avoid concurrent requests](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#avoid-concurrent-requests)） |
| 使用者操作同時數 | 1（複製失敗 log） | log 下載可能要好幾秒，不能卡住輪詢 |
| 同時請求總數上限 | 2（`MaxConcurrentRequests`；需求的硬上限 8 仍然遵守） | Q1 |
| 每分鐘請求數上限 | 60（`MaxRequestsPerMinute`；任何 60 秒滑動視窗內，含 304） | 見下方說明 |

**CPU 時間**：

- 次級限制有「每 60 秒真實時間最多 90 秒 CPU 時間」，官方說可以用總回應時間粗估。
- 本工具最多 2 條請求同時進行，上界是 2 × 60 = 120 秒。但使用者操作只有偶發的複製 log，輪詢那條序列化後不超過 60 秒。
- GitHub 會不會把同帳號其他工具的請求一起算進這個限制，文件沒寫。

**每分鐘上限 60 的依據**（可重算）：

1. 次級限制：REST **單一端點**每分鐘最多 900 點，多數 GET 算 1 點（[Rate limits › secondary](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#about-secondary-rate-limits)）。
   - 「單一端點」指路徑樣板還是具體 URL，官方沒有定義。
   - 304 算不算點數，文件也沒寫，所以保守地把 304 也算 1 點。
   - 就算所有請求都打同一個端點，60 也遠低於 900。
2. 預估負載：平常每分鐘約 5～6.5 次（§6.7），60 約是 9 倍以上的餘裕，足夠應付 F5 與冷啟動。
3. 冷啟動約 65～90 個請求（§6.7）：前 60 個依回應速度連續送出，第 61 個起要等最早那個請求滿 60 秒才放行，約 1～1.5 分鐘送完。這段期間先顯示本地快取的資料。

**優先序與老化**：

- 基本順序（高到低）：
  1. 使用者操作
  2. `repoRunning` 的 repo
  3. `pushed_at` 剛變動的 repo
  4. push 探測
  5. 其他到期的 runs 輪詢與 E6
  6. PR 清單與 PR 分支補抓
  7. workflow 清單、預設分支補抓、repo 完整清單
- 老化：排隊每滿 `PriorityAgingStep`（60 秒），優先序升一級，最高升到第 2 級。所以就算很多 repo 同時在跑、吃滿每分鐘上限，探測與 PR 清單也會在幾分鐘內送出，不會餓死。
- 同一級時，到期越久的先送。

### 6.4 低額度、限流與退避

**低額度拉長**：

- `ratio = remaining ÷ limit`。
- `remaining` 取最近 `QuotaSampleWindow`（60 秒）內、`x-ratelimit-resource` 為 `core` 的所有回應中的最小值，而且要在同一個 `x-ratelimit-reset` 視窗內。這是為了避免多區域處理造成的上下跳動，讓倍率忽大忽小。

```
k = 1                                         ratio ≥ 0.25
k = clamp(0.25 ÷ ratio, StretchMin, StretchMax)  ratio < 0.25（ratio = 0 時 k = StretchMax）
```

| ratio | k |
|---|---|
| 0.30 | 1 |
| 0.20 | 0.25 ÷ 0.20 = 1.25 → 下限 2 |
| 0.10 | 2.5 |
| 0.05 | 5 |
| 0.02 | 12.5 → 上限 8 |

`StretchMin = 2`、`StretchMax = 8` 是設計選擇（BuildMonitor 文件也是最多拉長 8 倍）。官方提醒不要寫依賴精確剩餘數的邏輯，所以跨過 25% 才開始拉長，一開始就是 2 倍。

**錯誤分類**（只用在 `api.github.com` 的回應；依序判斷）：

依據：[Rate limits › exceeding](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#exceeding-the-rate-limit)、[Best practices › handle rate limit errors](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#handle-rate-limit-errors-appropriately)、[Troubleshooting › resource not accessible](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api#resource-not-accessible)。

| 順序 | 條件 | 判定 | 行為 |
|---|---|---|---|
| 1 | 403 或 429，且有 `retry-after` 或 `x-ratelimit-remaining == 0` | 限流（有 retry-after 算次級；只有 remaining=0 算主額度） | **全域暫停**。兩個 header 都有時取較晚者：`max(retry-after 秒, reset − Date + RateLimitResetMargin)`；算出來 ≤ 0 時，用 `MinRateLimitWait`（60 秒） |
| 2 | 429（沒有上述 header），或 403 的 body `message` 含「secondary rate limit」（不分大小寫） | 次級限流 | 全域暫停，退避等級見下方 |
| 3 | 403，body `message` 以「Resource not accessible by」開頭 | 權限不足 | 只停**這個輪詢目標**（例如只停 E7、E4 照常），標示缺的權限：讀 `X-Accepted-GitHub-Permissions`（逗號分隔是同一組都要、分號分隔是多組擇一），classic／OAuth token 讀 `X-Accepted-OAuth-Scopes`。每 `PermissionRetryInterval` 再試一次 |
| 4 | 其他 403 | 存取被拒（例如組織政策、SSO） | 同第 3 列，另外標示 body `message` 原文 |
| 5 | 60 秒內有 3 個以上不同 repo 落在第 4 列 | 可能是沒寫明的次級限流 | 全域暫停 `MinRateLimitWait` 一次（不倍增），寫 error.log（Q23） |

- 判斷順序很重要：權限錯誤要排在「無法分類的 403」之前，否則永遠走不到。
- 官方只說次級限流時「錯誤訊息會指出是次級限制」，沒有給原文。第 2 列的字串與第 5 列的規則都是推論加保守處理，實作時記錄實際收到的訊息再修正。
- `X-Accepted-GitHub-Permissions` 是「這個端點需要什麼權限」，正常回應也可能帶，所以不能單靠它判斷權限錯誤。
- 全域暫停期間**所有**請求都不送（包括其他 repo）。官方提醒限流中繼續送請求可能讓整合被封鎖，反覆忽略錯誤也可能被停權。
- 沒有 `retry-after` 時，橫幅上的時間是「程式預定重試的時間」，不是 GitHub 公布的恢復時間，文字會照實寫。次級限流沒有可查詢的狀態。

**次級限流的退避等級**：

- 第 n 次（n 從 1 起）的等待時間：`min(SecondaryBackoffInitial × 2^(n−1), SecondaryBackoffMax)`，依序是 60、120、240、480、960 秒。
- 第 5 次起固定 960 秒（16 分鐘），並在主畫面顯示「持續被限流」。
  - 官方建議重試若干次後就停止並報錯，具體次數沒有規定，這裡取 5 次。
  - 之後仍每 16 分鐘試一次（每小時不到 4 個請求），不完全停止，因為這是常駐監看工具（Q22）。
- **降級**：連續一段不短於上一次等待時間、而且沒有任何限流回應的期間過去後，n 才減 1；不是遇到一次成功就歸零。這是為了避免限流時好時壞時，永遠停在 60 秒、每分鐘撞一次。

**單一目標的其他錯誤**（5xx、422、JSON 解析失敗）：

- 只讓該目標退避：`下次間隔 = max(正常間隔, min(上次間隔 × 2, RepoErrorBackoffMax × k))`。
- 退避後的間隔不會比正常間隔短。
- 成功一次就恢復正常間隔。
- 422 不一律當成參數錯誤（文件說也可能是「endpoint has been spammed」），一樣寫 error.log。

**GitHub 持續異常**：連續 `ServerErrorBadgeThreshold`（3）個 `api.github.com` 回應都是 5xx，中間沒有任何 2xx 或 304，就加角標，橫幅顯示「GitHub 回應異常 · 最後更新 HH:mm」。

**網路中斷**：

- 判定：連續 `OfflineThreshold`（3）次連線層錯誤（DNS、連線被拒、TLS、用戶端 `HttpTimeout` 逾時），中間沒有任何成功回應，就判定離線。用戶端逾時只算在這裡，不算在「單一目標錯誤」。
- 離線時：停止所有輪詢，改用 E10 探測，從 30 秒起倍增到 300 秒。Windows 回報網路可用（`NetworkChange.NetworkAvailabilityChanged`）時立即探測一次。
- 恢復時：立即全量刷新。

### 6.5 鎖定、睡眠、喚醒

| 事件 | 來源 | 行為 |
|---|---|---|
| 鎖定 | `SystemEvents.SessionSwitch`（`SessionLock`） | `locked = true`；所有間隔下限變 300 秒；通知改為暫存 |
| 解鎖 | `SessionSwitch`（`SessionUnlock`） | `locked = false`；立即全量刷新；暫存的通知合併成一則彙總（§9.5） |
| 睡眠 | `SystemEvents.PowerModeChanged`（`Suspend`） | 設 `suspended` 旗標，不排新請求；**1 秒的 tick 計時器不停** |
| 喚醒 | `PowerModeChanged`（`Resume`），或下方的備援 | 清除 `suspended`，立即全量刷新（網路可能還沒起來，失敗就走離線流程） |

實作注意（依 .NET 文件與 dotnet/runtime 原始碼）：

- `SystemEvents` 是靜態事件，程式結束前必須取消訂閱，否則會洩漏。
- 在 UI 執行緒、訊息迴圈啟動後（主視窗 `SourceInitialized` 之後）訂閱。依原始碼推論，這樣處理常式會被送回 UI 執行緒執行；WPF 與 WinForms 併用時是否如此沒有查證。所以：
  - 處理常式一律執行緒安全：只用 `Interlocked`／`Volatile` 設旗標，再把工作交給 Engine 的指令佇列。
  - 實作時在處理常式記錄 `ManagedThreadId`，和 UI 執行緒比對一次。
- 收到 Suspend 後系統只給約 2 秒，所以處理常式只做上面那些快速動作。
- **喚醒的備援**（推論，未實測；手動測試 M2）：
  - `PowerModeChanged` 不處理 `PBT_APMRESUMEAUTOMATIC`，無人值守喚醒（例如遠端喚醒）時不會有 Resume 事件。
  - 所以 Engine 用單調時鐘比對相鄰兩次 tick 的間隔：超過 `SleepGapThreshold`（120 秒，tick 本身是 1 秒），就當成剛喚醒。
  - 單調時鐘（QPC）在睡眠期間也會計時，所以睡醒後的第一個 tick 會看到很大的間隔；系統時間被往回調不會誤判。
- **鎖定偵測只用來省額度，不當作正確性依據**：
  - `SessionSwitch` 訂閱時不檢查 `WTSRegisterSessionNotification` 的回傳值。開機自啟太早時，這個註冊可能失敗而不報錯（文件推論，未實測），鎖定事件就永遠不會來。
  - 後果只是鎖定期間照常輪詢、照常彈通知，不會漏資料。列入手動測試 M12。
- 程式執行中改了 Windows 時區：收到 `SystemEvents.TimeChanged` 時呼叫 `TimeZoneInfo.ClearCachedData()`。改時區會不會觸發這個事件沒有查證，列入手動測試 M11。

### 6.6 全量刷新

- 觸發來源：F5、系統匣「立即刷新」、解鎖、喚醒、離線恢復。
- 內容：push 探測、所有監看中 repo 的 runs 與 PR 清單，一律排入「現在到期」。照樣帶 ETag，受每分鐘上限與優先序控制。
- repo 完整清單與 workflow 清單仍依各自的週期，例外見下一點。
- 暫停模式（§6.2）沒有週期性的完整重抓，也沒有啟動時的那一輪。這次執行還沒抓完過清單時（資料庫剛重建、以暫停模式啟動），全量刷新用一輪完整重抓（§5.3）代替探測：探測只有最近 push 的第 1 頁，repo 超過一頁時，其他 repo 的失敗算不進總狀態。
  - 額度：清單 A、B 各自每 100 個 repo 1 個請求，比探測多的只有第 2 頁以後的分頁，repo 不超過一頁時一樣多；抓完之後回到只送探測。
  - 分頁中途失敗時，已抓到的分頁照常寫入（§5.4）。暫停中不自動重試（被限流時例外：全域暫停結束後重抓），下一次全量刷新再抓；解除暫停時立即補做（清單在等錯誤重試時例外，見下一點）。
  - 這兩種情況照舊送探測：清單在等錯誤重試（§6.1）；重建資料庫的退避期間（§14.3，抓回來的清單會被下一次重建清掉）。
- 第一次載入：載入時資料庫裡沒有 repo（第一次執行、資料庫剛重建），所有刷新模式都一樣。下列都成立之前，總狀態不會是「全部成功」（§7.3）：
  - 完整清單抓完一輪。一直抓不完就一直不成立：清單確實不完整。
  - 每個監看中的 repo 都查過一次 E4。等錯誤重試的不等（有問題標示）；一直查不到的最多等 `StaleDataThreshold`，從開始監看這個 repo 起算。
  - 沒有第一次都還沒送過的 repo 目標（E3、E7、E5、PR 分支補抓、stale 首次檢查）：失敗可能只有這些補抓看得到。stale 首次檢查已經查過 E3（同一個網址）的 repo，排在 `WorkflowsRefresh` 之後的 workflow 清單是下一次定期重查，不算還沒送過；下面兩種情況仍然要等，最多等到它送出：離到期不超過 `LockedMinInterval`（有新的 push 等原因馬上要送的，新的 workflow 的失敗可能只有接著的補抓看得到，而鎖定會把它往後延最多這個時間）；這個 repo 有目標最近一次送出沒有拿到答案（5xx、連線失敗、限流等，失敗可能只有它看得到；403、404 有自己的錯誤狀態，不算）。其他情況只看有沒有送過：送過但沒有拿到答案也算送過，可能先報全部成功，等重試才變紅（[已知限制](../known-limitations.zh-TW.md)第 33 項）。
  - 成立一次就不再適用，之後才出現的 repo 不會讓總狀態閃回無資料。資料庫裡有上一次的清單時不適用，重新啟動的總狀態照舊。

## 7. Run 狀態對應與彙總

### 7.1 status／conclusion 對應

run 物件的 `status` 與 `conclusion` 在 schema 裡是沒有 enum 的字串（可為 null）。值的來源是：`status` 查詢參數的允許值、check suite schema，以及 [status checks 參考頁](https://docs.github.com/en/pull-requests/reference/status-checks#check-statuses-and-conclusions)。

`startup_failure` 的位置：checks 指南、check suite schema、GraphQL、workflow_run webhook 四個官方來源都把它放在 conclusion；只有 status checks 參考頁的表格列在 status，而那張表連 failure 都列成 status，可信度低。套用到 workflow run 屬推論，保守起見兩個欄位都檢查。

| status | conclusion | 顯示狀態 | 判定類別 | 圖示（形狀＋顏色） |
|---|---|---|---|---|
| `queued`、`requested`、`pending` | — | 排隊 | 未完成 | 空心圓＋中心點，Warning |
| `in_progress` | — | 進行中 | 未完成 | 3/4 圓弧旋轉（唯一的動畫），Warning |
| 其他非 `completed` 的值（不認得） | — | 未知（顯示原字串） | 未完成 | 空心圓＋問號，Warning |
| `waiting` | — | 等待核准 | 等待 | 圓＋時鐘指針，Warning |
| `completed` | `action_required` | 等待核准 | 等待 | 同上 |
| `completed` | `success` | 成功 | 成功 | 實心圓＋✓，Accent |
| `completed` | `failure` | 失敗 | 失敗 | 實心圓＋✕，Danger |
| `completed` | `timed_out` | 失敗（逾時） | 失敗 | 同上 |
| `completed`（或 status 本身是 `startup_failure`） | `startup_failure` | 失敗（啟動失敗） | 失敗 | 同上 |
| `completed` | `cancelled` | 取消 | 灰 | 空心圓＋斜線，Text Muted |
| `completed` | `skipped` | 略過 | 灰 | 空心圓＋短橫線，Text Muted |
| `completed` | `neutral` | 略過（neutral） | 灰 | 同上 |
| `completed` | `stale` | 略過（stale） | 灰 | 同上 |
| `completed` | null 或不認得的值 | 未知（顯示原字串） | 灰 | 空心圓＋問號，Text Muted |
| null | — | 未知 | 未完成 | 空心圓＋問號，Warning |

- **不認得的狀態，在完成之前一律當「未完成」**（黃燈），避免 GitHub 新增一個代表執行中的值時，系統匣誤顯示綠燈。只有 `completed` 而且 conclusion 不認得時才歸灰。
- 官方說明：
  - `pending`：碰到 concurrency group 上限
  - `waiting`：在等 deployment protection rule
  - `requested`：已建立但還沒進佇列
  - 以上三者都只有 GitHub Actions 會設定
  - `stale`：GitHub 因執行過久而標記
  - `action_required`：「check run 完成時附帶了需要執行的動作」，官方定義和 fork PR 的核准沒有連在一起
- 需求要把 `waiting`／`action_required` 當成「等待核准」。待核准的 fork PR run 實際上是 `waiting` 還是 `completed` 加 `action_required`，沒有查證，列入驗收實測。
- 沒見過的值寫一次 error.log（每個值只記一次），不丟例外。官方把「新增 enum 值」歸類為非破壞性變更，就算固定 API 版本也可能出現新值。
- 未完成的 run 不會永遠卡著：官方限制任何 run 最多 35 天，到期會被取消（[Actions limits](https://docs.github.com/en/actions/reference/limits#existing-system-limits)）；等待核准超過 30 天會自動失敗。
- 每個圖示同時帶 `AutomationProperties.Name`（例如「失敗（逾時）」）與 tooltip，不只靠顏色與形狀。

### 7.2 要追蹤的 run

**追蹤鍵**：`(repo_id, workflow_id, head_repository.id, head_branch)`。同一個 workflow、同一個來源 repo、同一個分支上的 run，共用一個鍵。`head_branch` 為 null 的 run 不屬於任何鍵。

**哪些鍵要追蹤**（只看 `state == active` 的 workflow；E4 出現本地沒有的 `workflow_id` 時，先當成 active，並立即排 E3）：

1. **預設分支**：同時符合下列三個條件。
   - `head_branch == repo.default_branch`
   - `head_repository.id == repo.id`：排除 fork 開來、分支名剛好也叫 `main` 的 PR run
   - `event` 不是 `pull_request` 開頭的事件（`pull_request`、`pull_request_target`、`pull_request_review`、`pull_request_review_comment`）。這類 run 是在測 PR，不算預設分支本身的狀態；`pull_request_target` 的 `head_branch` 可能就是預設分支（推論）。其他事件（`push`、`schedule`、`workflow_dispatch`、`workflow_run`、`dynamic` 等）都算（Q26）。
2. **開啟中 PR 的分支**：E7 回傳的每個開啟中 PR，取 `(head.repo.id, head.ref)`，和 run 的 `(head_repository.id, head_branch)` 精確比對。不論 run 的 event 是 `pull_request` 還是 `push`，都算這個分支的 run。

**PR 分支補抓**（冷啟動時，PR 的最新 run 可能早已被擠出 E4 第 1 頁）：

- 每次 E7 回 200 後，挑出以下兩種 PR：
  - 本地沒有該分支任何 run
  - 本地最新 run 的 `head_sha` 不等於 PR 的 `head.sha`
- 對這些 PR 送 `GET .../actions/runs?head_sha={head.sha}&per_page=30`：帶 ETag、每個 head sha 只抓一次、低優先序。
- 補抓結果同樣受 §9.3 的時間界線約束，不會把舊失敗當成新通知。

**每個鍵的判定**：

- 本地為每個 run 保存每個看過的 attempt（`run_attempts` 表），所以重跑不會蓋掉前一次 attempt 的結論。
- **run 的決定性結論**：由新到舊看它的 attempt，取第一個「成功」或「失敗」類別的結論；灰色的 attempt 跳過。所以失敗之後重跑、再被取消，這個 run 仍算失敗（Q9）。
- **依 commit 分組**：
  - 鍵內的 run 依 `head_sha` 分組，各組依組內最大的 `run_number` 由新到舊排序。
  - 同一個 commit 同時由 `push` 與 `pull_request` 觸發時，兩筆 run 在同一組。
- `latest`：`run_number` 最大的 run。
- `keyPending`：`latest` 的最新 attempt 屬於「未完成」或「等待」類別。
- `lastDecisive`：由新到舊找第一個有決定性結論的組。組內任一 run 是失敗，這組就算失敗；否則只要有成功就算成功；整組都沒有決定性結論就往下一組找。
- `failing`：`lastDecisive` 是失敗，而且那一組最晚的 `updated_at` 在 `TrackedFailureMaxAgeDays`（90 天）內（Q6）。超過 90 天的失敗不算 `failing`，該鍵視為只有灰色結論。

這樣就滿足需求的四條規則：

| 需求 | 對應 |
|---|---|
| 每個 repo × workflow 在預設分支的最新 run | 規則 1 的鍵取 `latest` |
| 每個開啟中 PR 分支的最新 run | 規則 2 加 PR 分支補抓（**我解讀成「每個 PR 分支 × 每個 workflow」各取最新，Q5**） |
| 同分支較舊的失敗被較新的成功取代就不算 | 較新 commit 的成功組取代較舊的失敗。灰色結論（取消、略過）不會取代失敗，只有成功可以（需求原文是「被較新的成功取代」，Q9）。同一個 commit 的 push run 失敗、pull_request run 成功時，仍算失敗 |
| PR 合併、關閉或分支刪除後不算 | 規則 2 只看 E7 的開啟中清單，PR 一離開清單，這個鍵就不追蹤 |

- 重跑：同一筆 run 的 `run_attempt` 遞增、`run_number` 不變。被重跑的 run 只有在它本來就在最新的組時，才會影響追蹤。例如 #10 失敗、#11（較新的 commit）成功之後重跑 #10，追蹤看的還是 #11；#10 仍會出現在清單裡。
- 預設分支鍵缺資料時，用 E5 補抓（§4.2）。

### 7.3 整體狀態（系統匣顏色）

| 優先序 | 狀態 | 條件 | 顏色 |
|---|---|---|---|
| 1 | 失敗 | 任何一個追蹤鍵 `failing` | Danger |
| 2 | 進行中或排隊 | 任何一個追蹤鍵 `keyPending`（含等待核准，Q8） | Warning |
| 3 | 全部成功 | 至少一個追蹤鍵的 `lastDecisive` 是成功，而且沒有 1、2 的情況（Q4） | Accent |
| 4 | 無資料 | 以上都不成立：還沒登入、沒有監看中的 repo、還沒抓到資料，或所有鍵都只有灰色或未知結論 | Text Muted |

- 只有灰色或未知結論的鍵，不會阻擋綠燈，也不會讓狀態變綠（Q4）。
- 第一次載入還沒完成時（§6.6），「全部成功」改算無資料：還沒查到的 repo 可能是失敗的。
- 「失敗」與「進行中」可能同時成立（例如 #10 失敗、#11 正在跑）：顯示失敗色，tooltip 兩者都計。
- **連線問題用疊加角標**，不取代上面的顏色。角標條件：
  - 未登入（401）
  - 全域暫停（主額度用完或次級限流）
  - 離線
  - GitHub 持續回 5xx
  - API 版本錯誤

  角標是右下角小圓：深色底（Window Background）加 Warning 色「!」。
- **無法更新的 repo**：某個 repo 超過 `StaleDataThreshold`（1 小時）沒有任何成功回應（例如權限錯誤、404 後每小時重試）時：
  - 它的鍵仍以最後已知的「失敗」計入。
  - 不再計入「進行中」：已經不知道那筆 run 有沒有結束。
  - tooltip 與摘要列加一行「N 個 repo 無法更新」。
  - 不加角標：需求只對全域的連線問題加角標（Q24）。

### 7.4 摘要列與 tooltip 的計數

| 計數 | 定義 |
|---|---|
| N 筆執行 | 主清單目前的 run 數（§10.10），不受篩選影響 |
| X 進行中 | `keyPending` 的追蹤鍵數（Q12） |
| Y 失敗 | `failing` 的追蹤鍵數（Q12） |
| 最後更新 | 最近一次成功回應（含 304）的本地時間 `HH:mm:ss` |
| API 剩餘 a/b | 最近一次 `core` 回應的 `x-ratelimit-remaining`／`x-ratelimit-limit`。這份額度和 gh 等工具共用，數字會被其他工具吃掉 |

系統匣 tooltip（`NotifyIcon.Text`）：

```
IsItGreenYet
2 進行中 · 0 失敗 · 更新於 10:07
```

- 有角標或無法更新的 repo 時，再加一行原因，例如 `需要重新登入`、`離線`、`被限流，預定 10:45 再試`、`2 個 repo 無法更新`。
- `NotifyIcon.Text` 的長度上限，實作時以 .NET 10 文件確認；超過時先截短原因那一行。

## 8. 耗時與預估

### 8.1 耗時

- 已完成的 run：`updated_at − run_started_at`。`run_started_at` 缺值時用 `created_at`，並在 tooltip 註明。
- 官方沒有定義 `created_at`／`updated_at` 的語意，所以這是**推論**。`run_started_at` 在重跑時會重設，所以算出來的是最新一次 attempt 的耗時。
- 驗收時挑 3 筆已完成的 run，和網頁顯示的耗時比對（§18）。差超過 5 秒時：
  - 先查文件，找更準的來源。
  - 候選做法：run 第一次轉成 completed 時，呼叫一次 E8，以 `max(jobs.completed_at) − run_started_at` 為耗時並存起來（每筆 run 多 1 個請求）；jobs 為空時退回 `updated_at`。
  - `/timing` 已停用，不在候選內。
- 顯示格式暫定 `45s`、`3m 12s`、`1h 05m`。驗收比對網頁時一併確認格式（例如超過 1 小時要不要顯示秒）。

### 8.2 預估剩餘時間（ETA）

- 樣本：同一 repo、同一 workflow，已完成且結論是 `success` 的 run 耗時。存在 `duration_samples`，每個 `(run_id, run_attempt)` 一筆。
- 取最近 10 筆（`EtaSampleSize`，依完成時間）的中位數 `median`；偶數筆時取中間兩筆的平均。
- 樣本少於 3 筆（`EtaMinSamples`）時不預估，只顯示已執行時間。
- 進行中的 run：`elapsed = now − run_started_at`。
  - `elapsed ≤ median`：顯示「已執行 4m 12s · 約剩 3m」，細進度條 = `elapsed ÷ median`。
  - `elapsed > median`：顯示「已執行 9m 40s · 超過預估約 3m」，進度條滿格改用 Warning 色。
- **估算值不顯示成精確值**：
  - 剩餘時間與超過量一律前面加「約」，以分鐘為單位無條件進位：剩 2m10s 顯示「約剩 3m」，剛好 3m00s 顯示「約剩 3m」。
  - 不到 1 分鐘顯示「不到 1m」。
  - 需求的範例是「超過預估 3m」，這裡多了「約」字，以符合「不要把估算值顯示成精確值」。
  - 已執行時間是實測值，顯示到秒。
- 排隊中的 run 不預估，只顯示「排隊 1m 05s」（`now − created_at`）。

## 9. 通知

### 9.1 觸發條件（三項都可在設定關閉）

所有通知都以「**完成觀察**」為起點：某個 `(run_id, run_attempt)` 在本次執行中，**第一次被看到是完成狀態**的那一刻。可能有兩種：從未完成轉成完成，或第一次看到時就已經完成（新 repo、E5／E6 補抓、PR 分支補抓）。

| # | 條件（在完成觀察的那一刻判斷） | 預設 |
|---|---|---|
| N1 | 結論是失敗類別，而且這個 run 在那一刻屬於某個追蹤鍵（是 `latest`，或在 `lastDecisive` 那一組） | 開 |
| N2 | 結論是成功，而且 `actor.id == 我的 id`（需求原文是 actor，Q10）；不限追蹤範圍 | 開 |
| N3 | 你標了「完成時通知我」：判定類別變成成功、失敗或灰色（不再是未完成或等待）；通知後自動取消標記 | 開 |

- 同一筆 run 同時符合多項時只發一次。
- **追蹤範圍本身的變動不會發通知**。例如功能分支上 5 小時前失敗的 run，因為你剛開了 PR 而變成追蹤中，不會因此跳出通知。

### 9.2 去重

- 鍵：`(run_id, run_attempt, conclusion)`，存在 `cache.db` 的 `notified`，重啟後不重發。
- 重跑讓 `run_attempt` 遞增，就是新的一組，會再通知。

### 9.3 首輪靜默（時間界線）

需求是「啟動後第一輪輪詢不發通知，避免一開機就彈出一堆舊的失敗」。只看「第一次回應」不夠：E5、E6、PR 分支補抓會在之後才抓回舊失敗；程式執行中才出現的 repo，第一次被看到時又可能有真正的新失敗。所以改用時間界線：

- 每個 repo 有一個界線 `T0`：

  | repo 的來歷 | T0 |
  |---|---|
  | 程式啟動時就已存在（在 DB 裡，或第一次完整重抓就看到） | 程式啟動時間 |
  | 執行中第一次出現的新 repo id（新建、剛被加為協作者） | 程式啟動時間 |
  | 因為有新的 push 而從「略過」自動轉成監看 | 觸發轉換的那個 `pushed_at` |
  | 因為你的操作才開始監看（取消靜音、強制納入、改設定） | 操作的時間 |

- 完成觀察時，`updated_at < T0` 的 run 只寫進 `notified`（`suppressed = 1`），不發 N1、N2。
- 例外：N3（你明確要求的「完成時通知我」）不受界線限制（Q14）。
- 回 304 的請求不影響判斷，因為判斷看的是 run 的時間，不是第一次回應。
- `updated_at` 的語意沒有官方定義。如果完成後還會變動，舊失敗可能跨過界線而通知一次；去重鍵會保證最多一次。
- DB 損毀重建後，`notified` 是空的，但界線不會因重建而提早：一般仍是程式啟動時間，晚於啟動時間的界線沿用重建前的值，重建前靜音中的 repo 以重建的時間為界線；這次執行已經通知或記過的靠記憶體裡的去重紀錄擋下。所以不會一次跳出一堆舊通知。

### 9.4 合併與顯示

- **合併**：同一個 2 秒視窗（`NotificationMergeWindow`）內產生的通知合併成一則；提示視窗還開著時又有新的，就把內容合併成彙總並重新計時。
- **單筆提示的標題**：用 §7.1 的顯示狀態，例如「失敗：repo · workflow #123」、「成功：…」、「取消：…」。內文「display_title · 分支 · by actor」。
- **彙總提示**：
  - 標題「3 筆執行有變化（2 失敗、1 成功）」；有灰色結論時，括號裡另加「1 其他」。
  - 最多列 5 行（`SummaryToastMaxLines`），其餘顯示「還有 N 筆」。
- **點擊**：單筆開啟該 run；彙總中點某一行開該 run，點其他地方開主視窗。
- **停留時間與框線色**：

  | 結論 | 停留 | 框線 |
  |---|---|---|
  | 失敗，或含失敗的彙總 | 12 秒（3–120 可調） | Danger |
  | 成功 | 5 秒（2–60 可調） | Accent |
  | 灰色（取消、略過、未知） | 同成功 | Text Muted |

- 滑鼠停在提示上時暫停計時，移開後繼續剩餘時間。右上角有 ✕ 可以關掉。
- **外觀與位置**：沿用 SAM 的 `ToastWindow`：主螢幕工作區右下角，`Topmost`、不搶焦點、不出現在工作列；視窗標題 `IsItGreenYet`。
- 不用 Windows 系統通知，因為系統氣泡會被專注輔助吃掉（SAM design-notes 的紀錄）。

### 9.5 鎖定、離線、睡眠

| 情況 | 行為 |
|---|---|
| 鎖定期間 | 通知照常判定與去重，但不顯示，暫存起來 |
| 解鎖 | 暫存的通知合併成一則「鎖定期間的變化」；沒有暫存就不顯示 |
| 離線期間 | 沒有新資料，自然不會有通知 |
| 離線恢復、睡眠喚醒 | 恢復後抓到的變化照常通知（多筆就合併）。程式啟動時間的界線早已建立，不算首輪 |

### 9.6 檢查新版本

功能名稱是「檢查新版本」；「自動更新」是輪詢間隔的名稱，兩者無關。程式只通知，不下載也不替換自己，升級由使用者替換 exe。

**開關**：`checkForUpdates`（§14.2）預設開，在設定頁關閉（§11.2）。

- 關閉後完全不送這個請求：判斷與送出都讀設定物件本身，按下儲存之後就不會再有新請求。
- 請求進行中才關閉：已送出的收不回來，結果整個丟棄，不更新時間、不存 ETag、不通知、不算失敗。排隊中的提示也取消。
- 重新開啟不另外觸發，最晚 1 小時內由每小時的判斷接手。
- 設定檔讀不到而且原檔留著（`LoadFailedFileKept`）時，這次執行視為關閉：讀不到使用者的選擇，用預設值送出可能違反「關閉後完全不送」。

**到期**：

- 距離上次完成的檢查滿 `UpdateCheckIntervalDays`（3 天），或從沒檢查過。上次檢查時間存在 `lastUpdateCheckUtc`。
- 只看 UTC 牆上時間，不用計時器累計，因為電腦會睡眠。上次檢查時間在未來（時鐘被調回）視為到期。
- 失敗後 `UpdateCheckRetryFloor`（1 小時）內不到期，優先於上面的條件。失敗時間只放記憶體，不存進設定檔，所以重開 App 可能提早重試（[已知限制](../known-limitations.zh-TW.md)第 41 項）。

**什麼時候判斷**（不連網）：每 `UpdateCheckLocalInterval`（1 小時，單調時鐘只決定時機）一次；E1 驗證成功（含啟動時）、喚醒（§6.5 的兩種）、解鎖之後也各一次。「自動更新」設成「暫停」時照常判斷與送出。

**送出**：到期才送 E15，走輪詢那條線、經過節流（§6.3），不阻塞啟動。一定帶使用者的 token：沒有 token 時私有 repo 回 404，而 404 算完成。

| 結果 | 分類 | 上次檢查時間 | 1 小時下限 |
|---|---|---|---|
| 200（含缺 `tag_name`、缺 `html_url`）、304、404 | 完成 | 更新 | 清除 |
| 其他狀態碼、網路錯誤、轉址錯誤、JSON 壞掉、非取消的例外 | 失敗 | 不動 | 設成現在 |
| 已到期，但引擎已知離線、全域暫停或版本錯誤 | 不送，算一次嘗試 | 不動 | 設成現在 |
| 未登入、E1 驗證中、睡眠中、未到期 | 不送，不算嘗試 | 不動 | 不動 |
| 取消（程式結束） | 不算嘗試 | 不動 | 不動 |

**版本比較**：tag 去掉一個小寫 `v`，目前版本切掉第一個 `+` 之後的 build metadata，再照 SemVer 2.0.0 比較（含 prerelease；`1.10.0 > 1.9.0`）。tag 解析不了或缺少時，當成沒有新版並寫 log。目前版本解析不了時不送請求，比不出結果。

E15 不回 prerelease 與 draft，所以這兩種 release 不會通知；目前版本是 prerelease 時，較新的正式版照樣通知。

**通知**（依序判斷）：tag 解析不了或缺少 → 沒有新版；tag 不比目前版本新 → 沒有新版；不比 `lastNotifiedVersion` 新 → 已通知過（最新的 release 被撤下時，回到通知過的版本不會再通知；設定檔只記一個版本，較舊而沒通知過的版本也不通知，[已知限制](../known-limitations.zh-TW.md)第 45 項）；`html_url` 缺少或不是 `https://github.com/` 開頭（§10.7）→ 不通知並寫 log；其餘通知。

- 用同一個提示視窗，走 §9.4 的合併視窗與 §9.5 的鎖定暫存，不受 N1～N3 的開關影響。停留一律用失敗的秒數：只通知一次，5 秒容易錯過。
- 只有新版本時，解鎖後不算「鎖定期間的變化」。

| 內容 | 標題 | 行 | 點空白處 | 語氣 |
|---|---|---|---|---|
| 只有新版本 | `有新版本：{版本}` | `點這裡開啟 release 頁面`（開 release） | 開 release | 灰色 |
| 新版本加 1 筆 run | run 的標題 | run 內文，加一行 `有新版本：{版本}（點這裡開啟）`（開 release） | 開 run | 照 run |
| 新版本加多筆 run，或鎖定彙總 | 既有標題 | 既有的行，加同一行（放最後，行數超過上限時被省略的是 run） | 開主視窗 | 照 run |

- `{版本}` 不含 `v` 與 build metadata。
- 提示真的交給 App 之後才記 `lastNotifiedVersion`。200 當下就更新上次檢查時間，所以通知前程式結束時，最多 3 天後回 200 再通知，不會遺失（[已知限制](../known-limitations.zh-TW.md)第 40 項）。
- 交給 App 就算通知過，引擎不知道使用者有沒有看到：不在電腦前時，提示消失後這個版本不會再通知（[已知限制](../known-limitations.zh-TW.md)第 44 項）。
- Engine 不寫設定檔：由事件交給 App，回 UI 執行緒才改設定物件與存檔。存檔失敗只寫 error.log，記憶體的值保留，下一次成功的儲存會順便寫出。

**ETag**：存在 `http_cache`（§14.3）。有上次檢查時間才帶 `If-None-Match`：設定檔重置之後不帶，才不會被 304 蓋住。

| 情況 | ETag |
|---|---|
| 200，不需要通知（沒有新版、已通知過、tag 或 `html_url` 有問題） | 立刻存 |
| 200，要通知 | 不存，下一次回 200 時已通知過才存：`lastNotifiedVersion` 由 App 非同步存檔，沒存到時要是回 304，就沒有內容可以再通知 |
| 304、404、失敗 | 不動 |

**失敗隔離**：這個請求不經過一般輪詢的結果處理，所以不管回什麼，都不影響「!」角標、離線、全域暫停（和 §6.4 的差異見 [spec-deviations.md](../spec-deviations.md)）、未登入、5xx 橫幅、版本錯誤、額度與最後更新時間，也不跳視窗、橫幅或提示。log 見 §15。

### 10.6 觸發說明

| event | 顯示 | 可點 |
|---|---|---|
| `pull_request` | `Pull request #17` | PR 編號 → `{repo.html_url}/pull/17` |
| `pull_request`，但沒有 PR 編號 | `Pull request` | 否 |
| `push` | `Commit dcf27ad`（`head_sha` 前 7 碼） | → `{repo.html_url}/commit/{head_sha}` |
| `schedule` | 排程 | 否 |
| `workflow_dispatch` | 手動觸發 | 否 |
| 其他（例如 `dynamic`、`workflow_run`、`pull_request_target`、`release`） | 原始 event 名稱 | 否 |

PR 編號的來源（Q18）：

1. `event` 是 `pull_request` 時，先在 E7 的開啟中 PR 裡找 `head.sha == run.head_sha`、而且 `head.repo.id == run.head_repository.id` 的 PR，用它的編號（不多花請求）。
2. 找不到時，退回 run 的 `pull_requests[0].number`；有多個時，tooltip 列出全部。官方說這個陣列只含「head 相符且仍開啟」的 PR，不一定是觸發這次 run 的 PR。
3. PR 關閉後 API 就不再回傳，所以第一次觀察到的編號存進本地 `runs.pr_numbers`，之後照樣顯示。
4. 從來沒觀察到時（fork 來的 PR 的 `pull_requests` 為空且比對不到，或程式第一次看到時 PR 已關閉）就留白，不推測。
- 2026-10-24 實測，你的 repo 出現過 `dynamic` 事件，照「其他」顯示。

### 10.7 連結

- 所有網頁連結都以 API 回傳的 `html_url` 為基底：
  - run：`run.html_url`
  - repo、PR、commit：`repo.html_url`
  - 分支：`head_repository.html_url + "/tree/" + 分支名`，分支名依 `/` 切段後各段 URL 編碼
- 開啟前驗證 scheme 是 `https`、host 是 `github.com`；不符合就不開，並寫 error.log（API 資料不應被當成任意網址開啟）。
- 用 `Process.Start`（`UseShellExecute = true`）交給預設瀏覽器。

### 10.8 開始時間

以 `run_started_at`（缺值用 `created_at`）換成本地時區（`TimeProvider.LocalTimeZone`），依序判斷：

| 條件 | 顯示 | 例 |
|---|---|---|
| 開始時間晚於現在（時鐘誤差） | 剛剛 | — |
| 不到 `JustNowThreshold`（60 秒） | 剛剛 | — |
| 不到 1 小時 | N 分鐘前 | 40 分鐘前 |
| 本地日期是今天 | 今天 HH:mm | 今天 08:32 |
| 今年 | M/d HH:mm | 10/23 23:50 |
| 更早 | yyyy/M/d | 2025/12/31 |

- 「1 小時內」優先於「今天」：00:30 看 23:50 開始的 run，顯示「40 分鐘前」；01:10 再看，顯示「10/23 23:50」。
- tooltip 顯示完整的本地時間 `yyyy-MM-dd HH:mm:ss`。
- 相對時間每 30 秒重算一次文字，不重排清單；進行中的已執行時間每秒更新。

### 10.9 ⋯ 選單與右鍵選單

| 項目 | 出現條件 | 行為 |
|---|---|---|
| 開啟 run | 一律 | `run.html_url` |
| 開啟 PR | 有 PR 編號 | PR 頁 |
| 開啟 commit | 一律 | commit 頁 |
| 複製 run 網址 | 一律 | 複製 `run.html_url` |
| 複製失敗 log | 結論是失敗類別 | 見下方說明 |
| 這筆完成時通知我 | 判定類別是「未完成」或「等待」 | 標記存進 `watched_runs`，列上顯示小鈴鐺；再點一次取消 |
| 靜音此 repo | 一律 | 寫入 `repo_overrides`，立即從清單與計數中移除；到 repo 管理頁可取消 |

**複製失敗 log**：

1. 用 E8 取 `filter=latest` 的 job，挑出結論是 `failure` 或 `timed_out` 的。
2. 逐一用 E9 下載，每個 job 只保留最後 `LogTailLines`（預設 200）行：用串流讀取，只留尾端。
3. 組成「=== job 名稱（結論）===」加上 log 尾端，複製到剪貼簿。
4. 沒有失敗的 job 時（例如 `startup_failure` 可能根本沒有 job）顯示「這次 run 沒有失敗的 job log 可複製」。
5. log 只放在剪貼簿，不寫入任何檔案。

複製到剪貼簿失敗（剪貼簿被其他程式佔用）時，重試 3 次，每次間隔 100 毫秒，仍失敗就顯示訊息。

### 10.10 清單行為

- **主清單的內容**（四者的聯集，去掉重複）：
  1. 每個監看中 repo 最近一次 E4 第 1 頁回應裡的 run（每個 repo 最多 30 筆）
  2. 各追蹤鍵的 `latest` 與 `lastDecisive` 組的 run
  3. 被標記「完成時通知我」的 run
  4. 本地判定為未完成或等待、還在 E6 追蹤中的 run

  被靜音、被略過或已移出的 repo，它的 run 不顯示。本地 DB 裡其他較舊的 run 不顯示（只供計算用）。
- **排序**：開始時間（`run_started_at`，缺值用 `created_at`）由新到舊；同時間再依 run `id` 由大到小。API 文件沒寫回傳順序，所以自己排；和網頁順序是否一致，在驗收時確認。
- **延後重排**：輪詢更新時，若右鍵選單開著，或滑鼠停在某列的按鈕上：
  - 既有列的內容照常原地更新（狀態、時間文字）。
  - 新增、移除、重排延後，選單關閉或滑鼠移開後才套用，最多延後 30 秒（`ReorderFreezeMax`，同 BuildMonitor）。
- **寬度不夠時依序隱藏**：觸發者 → 分支 chip → 時間細節（只留耗時）。
  - 比較的是列內容寬度：清單的可用寬度（扣掉邊距與捲軸）再扣掉每一列的內距與外框（附錄 B）。
  - 初始斷點 860／720／560 DIP，實作時依實際版面截圖調整。
  - repo 名稱與狀態圖示永遠可見。
- 清單用虛擬化（`VirtualizingStackPanel`），沿用 SAM 的 `Style.ListBoxItem.Record` 與細捲軸。

## 13. 認證與機密

### 13.1 gh CLI（預設）

- 執行 `gh auth token --hostname github.com`：
  - `CreateNoWindow`，只讀 stdout，去掉結尾換行。
  - stderr 不解析（新版 gh 可能在這裡印出到期警告），也不寫進任何 log。
  - 逾時 10 秒。
  - 不用新版才有的旗標（本機是 gh 2.102.0）。
- 結果判斷：
  - 找不到 `gh`（`Win32Exception`）→「沒有安裝 gh」。
  - 退出碼非 0（找不到 token 時是 1）→「gh 沒有登入」。
- token 只放在記憶體。啟動時取得，收到 401 時重新取得。
- **環境變數**：
  - `gh auth token` 會優先回傳環境變數 `GH_TOKEN`、`GITHUB_TOKEN`，所以拿到的不一定是 gh 自己存的 OAuth token。程式不假設 token 的前綴或權限，權限問題一律以回應 header 判斷。
  - 啟動時檢查本行程有沒有這兩個變數。有的話，設定頁標示 token 來源，401 時的橫幅也改成對應文字（§10.2）。
  - 已在執行的行程收不到環境變數的修改，所以要重新啟動程式。
  - 設定「忽略環境變數」開啟時，執行 gh 的子行程會先移除這兩個變數（Q32）。
- 新版 gh 的 token 可能會自動刷新，舊值隨時可能被撤銷，所以不長期依賴某個值。
- OAuth token 一年沒用會被自動撤銷；同一使用者、同一 OAuth app、同一組 scope 最多同時有 10 個 token，超過時舊的會被撤銷（[Token expiration and revocation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation)）。你在很多台機器登入 gh 時，本機的 gh token 可能被撤銷，所以 401 要當成會發生的常態處理。

### 13.2 401 處理（避免連續送出無效憑證）

官方說明：短時間內偵測到多次無效憑證後，API 會暫時拒絕該使用者**所有**的驗證嘗試，包含有效的憑證（[Authenticating › failed login limit](https://docs.github.com/en/rest/authentication/authenticating-to-the-rest-api#failed-login-limit)）。這會連帶擋掉你的 gh、Claude Code、codex。

1. 收到 401：重新取得 token。取得的值和原本不同，就用新值重送這個請求**一次**。
2. 值相同、取不到，或重送仍 401，就進入「未登入」狀態：
   - 停止所有輪詢
   - 顯示橫幅與系統匣角標
   - 既有資料不清空
3. 「未登入」期間：
   - gh 模式：每 5 分鐘在本機執行一次 `gh auth token`（不打 API）。token 改變時才用 E1 驗證一次，成功就恢復輪詢。
   - PAT 模式：等你在設定貼上新的 PAT。
   - 「重新檢查」按鈕：立即重新取得 token，並用 E1 驗證一次。這是手動按才送的單一請求，不會變成連續重試。

### 13.3 PAT（替代方案）

- 存在 Windows Credential Manager：
  - 一般認證（`CRED_TYPE_GENERIC`），目標名稱 `IsItGreenYet:github.com`。
  - `CRED_PERSIST_LOCAL_MACHINE`：只在這台電腦、同一使用者的登入工作階段看得到，不漫遊。`CRED_PERSIST_ENTERPRISE` 會漫遊，不用。
  - blob 上限 2,560 bytes（`CRED_MAX_CREDENTIAL_BLOB_SIZE`），寫入前檢查長度。
  - 讀不到時（`ERROR_NOT_FOUND`）視為「尚未設定 PAT」；`ERROR_NO_SUCH_LOGON_SESSION` 顯示明確的錯誤。
  - `CredReadW` 回傳的緩衝區，一律在 `finally` 裡 `CredFree`。
- `settings.json` 只記 `authMode`（`ghCli` 或 `pat`），不存 token。
- 和 DPAPI（`ProtectedData`，CurrentUser）比較：
  - 兩者都綁目前使用者，也都不用裝套件（`ProtectedData` 已在 Windows Desktop 共享框架中）。
  - 選 Credential Manager 的理由：不用另外存密文檔案，使用者也能在 Windows「認證管理員」看到與刪除。
- README 寫明 fine-grained PAT 的設定方式：
  - resource owner 選自己
  - repository access 選全部，或選指定 repo
  - 權限：Actions read、Metadata read、Pull requests read（不需要 Contents read，Q2）
- README 也寫明限制：
  - 一把 PAT 只能對應一個擁有者
  - 組織 repo 的 outside collaborator 要用 classic PAT
  - 其他人擁有、你只是 collaborator 的私有 repo，推論讀不到

### 13.4 日誌遮罩

- `api.log` 不記 header，也不記 body。
- `SecretRedactor` 套用在 `api.log`、`error.log` 的每一行寫入：
  1. 把目前使用中的 token 原值換成 `***`（精確比對）。
  2. 再用樣式比對補強：`gh[opusr]_[A-Za-z0-9]{20,}`、`github_pat_[A-Za-z0-9_]{20,}`。前綴依 [GitHub's token formats](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github#githubs-token-formats)：OAuth `gho_`、classic `ghp_`、fine-grained `github_pat_`。
  3. `Authorization:` 後面的內容一律換成 `***`。
- 非 `api.github.com` 的 URL（log 的簽名下載網址）一律寫成 `host/path?***`。
- 例外訊息寫進 error.log 之前，也經過遮罩。
- 測試：用假 token 走過所有會寫 log 的路徑（成功、304、401、403、轉址、簽名下載、例外），斷言兩個 log 檔都找不到 token 原文與簽名參數（§17）。

- 同 SAM：改名為 `cache.db.corrupt-<yyyyMMddHHmmss>.bak`（WAL 等附屬檔一併搬走），重建空白資料庫，主畫面顯示 §10.2 的警告。
- 備份上限：編號備份最多 `MaxCorruptBackups`（5）份，滿了改名到固定檔名 `cache.db.corrupt-latest.bak`，覆寫上一次的這個檔與它的附屬檔，總量最多 6 份。只算程式產生的兩種檔名（`.corrupt-<14 位數字>.bak`、`.corrupt-<14 位數字>-<序號>.bak`），使用者自己命名的檔案與 latest 都不算；舊版留下的編號備份也算名額、不會自動清除，所以總量可能更多。程式絕不刪、不覆寫任何編號備份。搬檔前先確認主檔與它的附屬檔動得了；要存到 latest 時，也確認 latest 與它的附屬檔動得了（別的程式開著，或 latest 與它的附屬檔是唯讀，都算動不了）。動不了就什麼都不動：監看引擎退避後重試，App 啟動時由初始化發現的則顯示錯誤後結束。附屬檔先搬，主檔最後才離開路徑。
- 留檔規則：第一次損毀一定改名保留。新的資料庫持續讀到損毀的重試（退避見 `docs/spec-deviations.md` 的「快取資料庫持續損毀時的退避」），這份檔是這個程序自己重建的、之後沒設過靜音或強制納入（寫入失敗不算）、磁碟上至少已有 1 份編號備份、當下用唯讀連線也讀不到 `repo_overrides` 的資料列，才直接刪掉（連同附屬檔）再重建，不留檔；刪之前先寫 `error.log`（檔案大小與編號備份份數，不寫內容），橫幅仍指向這次執行最後留下的那份。其他情況一律改名保留。暫停時規則相同。
- 快取丟了只會重抓；**靜音與強制納入會一起遺失**，警告文字要寫明這點。
- 時間界線不會因重建而提早（§9.3），所以重建後不會一次跳出一堆舊通知。

### 14.4 api.log

格式（Tab 分隔，一個請求一行）：

```
2026-10-24T10:07:33.123+08:00	GET	/repos/{owner}/{repo}/actions/runs?per_page=30	304	core 4870/5000	182ms
```

- 欄位：本地時間、方法、路徑加查詢字串、狀態碼、`x-ratelimit-resource` 與 remaining/limit、耗時。
- 有轉址時加 `→ 新位置`（非 api.github.com 的寫成 `host/path?***`）；有 `retry-after` 時加 `retry-after=N`；全域暫停與恢復各記一行 `# paused until …`。
- 不記 header、不記 body。路徑會含 repo 名稱，這是本機檔案，不進版控。
- **輪替**：
  - 超過 2 MiB 時改名為 `api.1.log`，舊的依序往後推，舊檔保留 3 份（`ApiLogMaxBytes`、`ApiLogKeepFiles`）。連同目前的檔案共 4 份，最多約 8 MiB。
  - 以 §6.7 的上限每分鐘 6.5 行、每行約 120 bytes 估算：6.5 × 60 × 24 × 120 = 1,123,200 bytes／天。
  - 剛輪替完只有 3 份舊檔、共 6 MiB（6,291,456 bytes），約 5.6 天；4 份滿時 8 MiB，約 7.5 天。
  - 有 run 在跑時每分鐘會多幾行，天數會更短。

## 15. 例外處理

| 情境 | 行為 |
|---|---|
| gh 沒裝或沒登入、PAT 失效（401） | 主畫面橫幅加系統匣角標，引導你執行 `gh auth login` 或到設定貼 PAT（token 來自環境變數時，提示要重啟程式）；既有資料不清空；依 §13.2 不連續重試 |
| 權限不足（非限流的 403） | 只停那個輪詢目標（例如 E7），repo 管理頁與該 repo 的列標示缺的權限（`X-Accepted-GitHub-Permissions`，或 classic／OAuth token 的 `X-Accepted-OAuth-Scopes`）；其他目標與其他 repo 照常 |
| 主額度用完 | 全域暫停到 `x-ratelimit-reset`（用回應的 `Date` 計算），橫幅顯示預計恢復時間 |
| 次級限流（有 retry-after、429、訊息含「secondary rate limit」的 403） | 依 retry-after 全域暫停；沒有 retry-after 時依退避等級（60 秒起倍增，上限 16 分鐘，有降級條件）；橫幅寫明那是「程式預定重試的時間」 |
| 60 秒內 3 個以上 repo 出現無法分類的 403 | 全域暫停 60 秒一次，寫 error.log（Q23） |
| 網路中斷 | 保留最後資料，標示「離線 · 最後更新時間」；用 E10 探測，恢復後自動全量刷新；離線期間沒有新資料，不會發通知 |
| GitHub 持續回 5xx | 加角標與橫幅「GitHub 回應異常」，各目標照退避規則重試 |
| repo 改名（301，或 404 後重抓清單發現同一個 id 換了名字） | 跟隨到新位置：以 id 更新名稱，網址用新名稱重組 |
| repo 被刪除（404） | 重抓 repo 清單；連續兩輪完整清單都不見才移出（Q29）；還在清單中就標示並改成每小時重試 |
| repo 沒有任何 workflow | 不顯示在清單，repo 管理頁標示「沒有 workflow（或 Actions 已停用，無法分辨）」 |
| run 狀態為 `waiting`／`requested`／`pending`／`action_required` | 獨立狀態（排隊、等待核准），不算失敗也不算成功 |
| 結論為 `timed_out`、`startup_failure` | 算失敗 |
| 結論為 `cancelled`、`skipped`、`neutral`、`stale` | 不算失敗，灰色 |
| 沒見過的 status | 完成前當「未完成」（黃燈）；完成後結論不認得就歸灰；error.log 記一次 |
| fork 來的 PR（`pull_requests` 為空） | PR 欄位留白，不推測 |
| 同一個 commit 觸發多個 workflow | 各自一列 |
| 單筆 run 回 404（過了保留期、被刪掉） | 只把這筆標成「已不存在」並移出追蹤，保留本地紀錄，不影響 repo |
| GitHub 5xx、422、JSON 格式錯誤 | 只讓該目標退避（不短於正常間隔，上限 10 分鐘 × k）；JSON 錯誤時該筆回應丟棄、**不更新 ETag**；單筆 run 缺欄位時只略過那一筆；都寫 error.log |
| 列表回 204 或空 body | 當成 0 筆 |
| 轉址超過 3 次，或 HTTPS 轉 HTTP | 當成錯誤，不跟隨，error.log 記錄 |
| 400／410（API 版本錯誤） | 停止所有輪詢，加角標，橫幅提示更新程式 |
| 回應帶 `Deprecation`／`Sunset` | error.log 記錄，主畫面提示一次 |
| job log 拿不到（過期、job 還在跑、簽名網址過期） | 重新呼叫 E9 一次；仍失敗就顯示「拿不到這個 job 的 log（狀態碼 N）」；不影響 repo 狀態 |
| 剪貼簿被佔用 | 重試 3 次，仍失敗就顯示訊息 |
| 開啟連結的網址不是 `https://github.com/` | 不開，寫 error.log |
| Credential Manager 讀寫失敗 | 顯示錯誤，不改變目前的認證方式 |
| `%LOCALAPPDATA%` 不可寫 | 啟動時顯示錯誤並指出路徑（同 SAM） |
| DB 損毀 | 改名為 `.corrupt-<時間戳>.bak` 保留，再重建（同 SAM）；提示靜音與強制納入已遺失。編號備份最多 5 份，滿了存 `cache.db.corrupt-latest.bak` 並覆寫；持續損毀的重試依 §14.3 的留檔規則可能不留檔 |
| 設定檔損毀 | 改名保留，回落到預設值（同 SAM） |
| 重複啟動 | 喚回既有視窗（同 SAM） |
| 系統匣不可用 | 降級為一般視窗 |
| 開機自啟寫入失敗 | 顯示錯誤，設定回復為關閉（同 SAM） |
| 系統時間被往回調或往前調 | 排程用單調時鐘，不受影響；未來時間的 run 顯示「剛剛」；主額度等待時間用回應的 `Date` 計算 |
| 未預期例外 | UI 執行緒：寫 error.log，跳 MessageBox，程式繼續執行（同 SAM 的 `DispatcherUnhandledException`）。背景（Engine 迴圈、`UnobservedTaskException`）：寫 error.log；同一種例外 10 分鐘內只用橫幅提示一次，不跳 MessageBox；Engine 每一輪各自 try/catch，單輪失敗不會讓迴圈停掉 |
| 檢查新版本：404（repo 還沒公開或還沒有 release） | 靜默，只有 api.log 的那一行；不跳視窗、橫幅或提示，不影響「!」角標。算完成，3 天後才再查（§9.6） |
| 檢查新版本：限流、網路錯誤 | 靜默，同上；不全域暫停、不進離線。不算完成，最快 1 小時後重試 |
| 檢查新版本：其他失敗（401、一般 403、400、410、5xx、JSON 壞掉等） | 畫面一樣靜默，不進未登入、不停輪詢；另外寫 error.log 一行，同一種連續失敗只寫一次。最快 1 小時後重試 |
| 檢查新版本：非取消的例外 | 畫面一樣靜默：不跳橫幅，也不佔其他路徑的橫幅去重名額（§10.2），不影響輪詢；每次都寫進 error.log（含堆疊）。最快 1 小時後重試。cache.db 真的損毀時，改照上面「DB 損毀」處理 |
| 檢查新版本：tag 解析不了或缺少、`html_url` 缺少或不是 `https://github.com/` 開頭 | 算完成，當成沒有新版，寫 error.log 一行；存 ETag，內容沒變就回 304，不重複寫 |
| 檢查新版本：目前版本解析不了 | 不送請求，這次執行只寫 error.log 一次 |
| 檢查新版本：設定檔讀不到而且原檔留著 | 這次執行不檢查，設定頁顯示未勾選（§9.6） |
| 檢查新版本：存檔失敗 | 只寫 error.log，不跳訊息條；記憶體的值保留，下一次成功的儲存會順便寫出 |

## 17. 測試策略（Core，xUnit）

- HTTP 用假的 `HttpMessageHandler`，搭配 `tests/.../Fixtures/*.json`。fixture 全部是手寫的假資料：假 repo 名（例如 `octo-org/sample-app`）、假 id、假 sha、假 token，不含任何真實 token 或私人 repo 內容。
- 時間用自寫的 `ManualTimeProvider`：牆鐘、單調時鐘、本地時區可以分別設定，牆鐘可以往回調。
- DB 用暫存目錄（同 SAM 的 `TempWorkspace`）。
- 測試命名沿用 SAM 的中文句子式，例如 `較新的成功會取代較舊的失敗()`。

## 18. 驗收計畫

依需求的「驗收」一節：

1. `dotnet test` 全部通過；`tools/publish.ps1` 先跑測試、再產生圖示，最後一次輸出 `dist\IsItGreenYet.exe`（framework-dependent）與 `dist\IsItGreenYet-selfcontained.exe`（self-contained）兩個檔案。
   - 和 SAM 不同：SAM 一次只輸出一種，用 `-SelfContained` 切換；這裡一次輸出兩種。
   - 同 SAM 設 `PublishSingleFile=true`、`IncludeNativeLibrariesForSelfExtract=true`。沒設的話，WPF 的原生 DLL 與 `e_sqlite3.dll` 會留在 exe 旁邊，只複製 exe 會當掉；設了之後，原生 DLL 會在啟動時解壓到 `%TEMP%\.net\`。
   - 驗收時另外確認 `dist\` 裡只有這兩個 exe，並把它們各自單獨複製到空資料夾執行一次。
2. 用你的帳號實際執行：挑 2 個 repo，把最近 10 筆 run 的狀態、標題、分支、觸發者、耗時，和 GitHub 網頁逐一比對，做成比對表回報。
   - 一併確認：清單順序與網頁是否一致；耗時格式；觸發者顯示的是不是網頁上那個人。
   - 耗時另外挑 3 筆，比對差距是否在 5 秒內（§8.1）。
   - 比對表只在回報裡給你，不進版控（私人 repo 內容）。
3. 開一個測試 PR 觸發 CI，確認三件事：進行中的顯示、轉綠時的通知、系統匣狀態的變化。repo 與 PR 內容在動手前先跟你確認。
4. 執行 1 小時後，從 `api.log` 統計實際的請求數、304 比例、各端點分布，和 §6.7 的估算對照。另外確認：
   - E5 會不會回 304
   - runs 列表在 job 推進期間是否維持 304
5. 我無法自己測的項目，列成手動測試清單給你（初稿見下）。

另外，有機會時在沙盒 repo 實測（需要你同意建立測試 repo）：

- repo 改名後 API 的回應
- fork PR 的 run 欄位（`head_branch`、`pull_requests`、`head_repository`）
- 待核准 run 的 status／conclusion

### 18.1 手動測試清單（初稿，實作後補充）

| # | 項目 | 步驟 | 預期 |

### 19.1 第二階段：寫入操作

Core 預留介面。第一階段不實作，也不加空殼程式碼，只保證結構能接上：

```csharp
public interface IActionsWriter
{
    Task<WriteResult> RerunFailedJobsAsync(RepoRef repo, long runId, CancellationToken ct);
    Task<WriteResult> CancelRunAsync(RepoRef repo, long runId, CancellationToken ct);
}
```

| 動作 | 端點 | 權限 | 回應 |
|---|---|---|---|
| 重跑失敗的 job | [`POST /repos/{owner}/{repo}/actions/runs/{run_id}/rerun-failed-jobs`](https://docs.github.com/en/rest/actions/workflow-runs#re-run-failed-jobs-from-a-workflow-run) | Actions: write | 文件列 201；依 OpenAPI 描述，body 是空物件，不含新的 attempt 編號 |
| 取消 run | [`POST /repos/{owner}/{repo}/actions/runs/{run_id}/cancel`](https://docs.github.com/en/rest/actions/workflow-runs#cancel-a-workflow-run) | Actions: write | 文件列 202（非同步受理）、409（觸發條件文件沒寫） |
| 強制取消（cancel 沒反應時） | [`POST /repos/{owner}/{repo}/actions/runs/{run_id}/force-cancel`](https://docs.github.com/en/rest/actions/workflow-runs#force-cancel-a-workflow-run) | Actions: write | 文件列 202、409 |

- 二次確認：危險動作沿用 SAM 的兩段式樣式（`Style.Button.Danger.Subtle` → `Style.Button.Danger`）。
- 修改型請求之間至少間隔 1 秒（官方最佳實務），每個算 5 點次級限制。
- 送出後立即重新輪詢該 run。cancel 回 202 後，最多 5 分鐘才會變成 completed，UI 要有「取消中」的狀態。
- 限制：首次執行 30 天後不能重跑、最多重跑 50 次、workflow 停用時不能重跑。按鈕依這些條件事先停用；伺服器回應的 message 原樣顯示。
- fine-grained PAT 要另外加 Actions write；gh token 本來就有。

### 19.2 第二階段：命令列

`IsItGreenYet.exe status --json`：

- 讀 `cache.db` 的最新快照；加 `--refresh` 才打 API。輸出 JSON。
- 退出碼：0 全綠、1 有失敗、2 有進行中、3 無資料、4 錯誤（未登入、資料過舊）。
- 命令列模式不走單一實例喚回。

已知風險（第二階段實測）：IsItGreenYet.exe 是 WinExe（GUI 子系統），在互動式 PowerShell／cmd 下執行時，shell 可能不會等它結束，也不顯示輸出。可能的解法是 `AttachConsole(ATTACH_PARENT_PROCESS)`，或另外做一個主控台執行檔。

### 19.3 第三階段

- MCP server：讀 Engine 快照，提供查詢工具。
- Actions 以外的外部 check run：[`GET /repos/{owner}/{repo}/commits/{ref}/check-runs`](https://docs.github.com/en/rest/checks/runs#list-check-runs-for-a-git-reference)。fine-grained PAT 是否支援，官方文件互相矛盾，要實測；gh token（有 `repo` scope）可以用。
- 若外部服務是用 commit statuses 回報（不是 check runs），fine-grained PAT 開「Commit statuses: read」就能用 [`GET /repos/{owner}/{repo}/commits/{ref}/status`](https://docs.github.com/en/rest/commits/statuses#get-the-combined-status-for-a-specific-reference)。
- 長時間 `pending` 的 run，可以用 [`GET /repos/{owner}/{repo}/actions/runs/{run_id}/concurrency_groups`](https://docs.github.com/en/rest/actions/concurrency-groups#list-concurrency-groups-for-a-workflow-run)（Actions read）顯示被哪個 concurrency group 擋住。第一階段不做，列為可能的加強。
